# 事象の焦点と 1 対ずつの統合 — 群化の再設計 (2026-10-22、設計のみ)

この文書は全体見直し (`data/eval/eventnews_system_review_2026_10_22.md`) の推奨 4〜6
(S3 正解の作り直し・S4 焦点・S5 事象単位の統合・S1(a) 事後の点検・S2 判定の一本化) を、
実装できる粒度まで具体化したもの。**コード・設定・DB はまだ変えていない** (DB は SELECT のみ、
Ollama・Opus は不使用)。「同じ事象」の定義は [event_identity_definition.md](event_identity_definition.md)
が SSoT で、ここではそれに従う。

> 公開リポの文書なので、被害組織名・実インシデントの詳細は書かない (§8 の事例は型と製品名だけ)。
> 事象 id つきの明細は `data/eval/` 側 (gitignore) に置く。

## 0 要点

1. **事象の代表を「最初の報道に錨を下ろした焦点」で持つ**。焦点 = 最初の記事 (seed) の名前
   (CVE・被害組織・アクター・マルウェア・ツール) + 「焦点を支える記事」の過半が持つ名前 + 行為 (種別)。
   **焦点を共有しない記事は焦点を動かさない**。和集合は「関連する名前」として別に持つ。
2. 統合の判定を**焦点どうしの照合 (4 値)** から始める: 食い違い (別の CVE / 別の被害組織) → 結ばない、
   系統 (同じ CVE の修正 ⇔ 悪用) → 関係へ回す、弱い (片側の焦点が空・アクター名だけ) → 厳しい判定へ、
   支持 → 今の判定。**推移閉包をやめ、事象の組を確信度の高い順に 1 つずつ判定し、結ぶたびに焦点を更新**する。
3. **机上の当て (既知の誤り 18 組)**: 焦点の照合だけで 10 組 (食い違い 9 + 系統 1) を止め、
   既に on の関門 (伏字・一括勧告の橋・月次レポート) と重ねて **14 組** (+ 今の入力では辺が出ず再現しない 1 組)。残る 3 組は、焦点が空の 2 組
   (B の事象対の判定器で扱う) と、新しい定義では「同じ事象」になる第 n 報 1 組。
   正しい統合 62 組のうち止まるのは 2 組 (うち 1 組は新しい定義では「別の事象」)。
   ⚠ 18 組は設計を考えるときに見た標本なので、これは**上限寄りの見積もり**。新しい標本で測り直す (§6)。
4. 直近 30 日の統合 860 件に当てると、支持 634 (74%) / 弱い 120 (14%) / 食い違い 86 (10%) / 系統 20 (2%)。
   止まる統合は 106 件 (12%)。80 組の正解で「食い違い・系統」に入った組の 10/12 が誤統合だったので、
   **約 90 件の誤統合を止め、約 18 件の正しい統合を失う**見込み (粗い外挿)。
5. 焦点の大きさは統合先で中央値 2 / 90 パーセンタイル 7 / 最大 34 (和集合は 3 / 21 / **863**)。
   和集合が汚染されて関門が効かなくなる問題 (見直し §3.3) は、焦点では起きない。
6. 移行は **焦点の記録 (shadow) → 統合の照合を shadow → 食い違いだけ本番で止める → 事象対の判定器 → 分割 → 判定の一本化**
   の順。焦点の照合は正解が無くても入れられ、Opus は「止めた組が本当に誤りか」の確認 (約 100 組) だけで切り替えられる。
   正解の作り直し (記事対 600 + 事象対 200、Opus 約 1,700 回) はそれと並行で進め、事象対の判定器 (B) の前提にする。

## 1 前提

### 1.1 定義と目標

- 「同じ事象」= 同じ行為者 (原因) による同じ対象へのひとまとまりの出来事の報道の束。第 n 報は同じ事象、
  修正 ⇔ 悪用・KEV 追加、行政指導などの派生、同じアクターの別作戦、まとめは**別の事象** (関係で結ぶ)。
- 目標: **統合の適合率 95% 以上を優先**、群化の回収率 80% 以上 (同じ事象の定義の中で数える。系統の組は回収漏れに数えない)。
- 現状: 統合の適合率 80% (関門後 40 組、Opus)、今の関門で補正して推定 82%。回収 65% (alert 重複 56 組、偏った標本)。

## 2 A — 事象の代表を焦点で持つ

### 2.1 焦点の定義

事象 E の焦点 `focus(E)` は 3 つの部分からなる。

| 部分 | 中身 |
|---|---|
| **錨 (anchor)** | seed 記事 (事象を立てた記事。統合後は統合先の seed) の名前。seed に名前が無ければ、名前を持つ最初のメンバー |
| **育った名前 (grown)** | 「支持記事」の中で保有率 θ 以上の名前 |
| **行為 (kind)** | 支持記事の種別 (breach / advisory / exploitation) の多数決 (過半のときだけ。other・stats は数えない) |

- **名前の型**: 群化と同じ `JOIN_ENTITY_TYPES` (cve・victim_org・actor・malware_family・tool)。被害組織は
  `org_match_key` で法人格を畳み、別名判定 (`EVENTNEWS_ORG_IDENTITY`) が on なら別名も畳む。伏字の被害者は除く。
- **数えない記事**: まとめ記事 (event_kind=roundup / まとめの見出し) は焦点に一切寄与しない。
  一括勧告 (CVE が `FOCAL_CVE_MAX`=3 超) の記事は CVE だけ寄与しない (他の型は寄与する)。
- **支持記事**: 焦点の名前を 1 つ以上持つメンバー。焦点と何も共有しないメンバーは「外れ」で、焦点を動かさない
  (外れの数は §4 の分割の候補選びに使う)。
- **θ = 0.5** (支持記事の過半)。机上では θ=0.5 と「過半 かつ 2 件以上」の差は小さい (§8.4)。shadow で両方を記録して決める。
- **錨は落とさない**: 支持記事の過半が持たなくなっても、seed の名前は焦点に残る。これが「焦点が動くのを抑える仕組み」。
- **焦点の型**: 和集合 (`related_names`) は今までどおり持つ (表示の「関連する名前」・検索・関係の候補生成用)。

なぜ錨が要るか (実例): 製品の認証回避の CVE で立った事象が、同じ製品の**別の CVE** の記事を 40 件以上吸収したため、
保有率だけで焦点を取ると焦点が後から来た CVE に**乗り移っていた**。保有率方式 (錨なし) では、その後に来た同じ別 CVE の
記事 2 件が「焦点が一致する」として通ってしまう (§8.2 の 2 組)。錨つきなら焦点は最初の CVE のまま残り、両方止まる。

### 2.2 更新の規則

| 出来事 | 焦点の更新 |
|---|---|
| 事象が立つ (seed) | 錨 = seed の名前。行為 = seed の種別 |
| 毎時の参加 | 新しい記事が焦点と共有するなら支持記事に加え、保有率を数え直して育った名前を足す / 引く (錨は引かない)。共有しないなら「外れ」に数えるだけ |
| 統合 (B) | 統合先の焦点を土台に、吸収側の**支持記事のうち統合先の焦点と共有するもの**だけを支持記事に足して数え直す。吸収側の錨は統合先の錨にならない (育った名前の候補になるだけ) |
| 統合を戻す / 分割 | 残ったメンバーで焦点を作り直す (記事の参加順に再生する。純粋関数なので決定論で再現できる) |
| entity の再抽出・別名の昇格 | 週次の作り直しの段でまとめて再計算 (毎時は追わない)。差分は記録に残す |

焦点の計算は**記事の参加順の再生**で決まる純粋関数 `compute_focus(members_in_join_order, article_names, kinds, rule)`
とし、DB の値はそのキャッシュにすぎない (いつでも作り直せる)。

### 2.3 DB の持ち方

```sql
-- 事象の焦点 (キャッシュ。compute_focus で作り直せる)
CREATE TABLE IF NOT EXISTS event_item_focus (
    item_id        TEXT PRIMARY KEY,
    rule_version   TEXT NOT NULL,          -- θ・型・除外の規則の版 (表は本番の版だけ持つ。変種の比較は再現スクリプトで行う)
    anchor_article TEXT NOT NULL DEFAULT '',
    names_json     TEXT NOT NULL,          -- [{"type","value","origin":"anchor|grown","share"}]
    kind           TEXT NOT NULL DEFAULT '',  -- breach / advisory / exploitation / ''
    supporters     INTEGER NOT NULL DEFAULT 0,
    outsiders      INTEGER NOT NULL DEFAULT 0,
    updated_at     TEXT NOT NULL
);

-- 焦点が変わった記録 (追記のみ、180 日)。焦点の揺れの監視と、統合を戻したときの影響の追跡に使う
CREATE TABLE IF NOT EXISTS event_item_focus_log (
    id           BIGSERIAL PRIMARY KEY,
    item_id      TEXT NOT NULL,
    changed_at   TEXT NOT NULL,
    cause        TEXT NOT NULL,           -- seed / join / merge / undo / split / rebuild
    decision_id  BIGINT,                  -- cause=merge のとき event_merge_decisions.id
    added_json   TEXT NOT NULL DEFAULT '[]',
    removed_json TEXT NOT NULL DEFAULT '[]'
);
```

- `event_merge_decisions` に列を 2 つ足す: `focus_class` (support / weak / conflict / lineage) と
  `focus_json` (統合前の両側の焦点の写し)。判断の記録から「どの焦点で結んだか」が辿れる。
- 列を `event_items` に足さない理由: 焦点は規則の版で作り直すキャッシュで、事象の状態 (重要度・時刻) とは寿命が違う。
- §7 の 3 点セット: 消費者 = 統合の照合 (B)・事象の画面 (下記)、fill-rate 監査に
  「複数記事の事象のうち焦点が空でない割合」「外れ 20% 以上の事象の数」を 1 行ずつ、ラベルは既存の SSoT (org 正規化・event_kind) を参照。

### 2.4 焦点を使う側の変更点

| 使う側 | 今 | 焦点に替えた後 |
|---|---|---|
| 統合の CVE 不一致の関門 (`focal_cves_by_item`) | 3 件以下の記事の CVE の和集合。ハブで膨らんで効かない | 焦点の CVE の食い違い (§3.2 の照合の一部)。`cve_disjoint_gate` は照合に吸収して撤去 |
| ハブ関門 (`hub_core_cves`、既定 off) | 8 件以上・CVE 4 種超の事象だけ、30% 以上が持つ CVE | 焦点の一般化なので**焦点の照合が on になったら撤去** (同じ判断を 2 か所に持たない) |
| 毎時の群化の不変条件 (`_invariant_holds`) | 全メンバーが共有する名前が 1 つ以上 | 「候補記事が焦点と 1 つ以上共有する」に替える。全員共有は統合後の群で 44% が破れており、統合と同じ物差しにする。⚠ 毎時の参加は今の不変条件のほうが厳しい場合がある (3 記事目以降)。shadow で両方の判定を記録し、食い違いの組を Opus で見てから替える |
| 関係 (`EventFeatures`) | 和集合 (焦点の CVE だけは記事単位で 3 件以下) | cves・victims・subjects・malware・tools を焦点から取る。和集合は珍しさ (df) の分母にだけ使う。relation_model は特徴の分布が変わるので**学習し直し** (E の事象対の正解で) |
| 事象の画面 | 名前・CVE の一覧が和集合 | 「この事象の焦点」(錨と育った名前) を先頭に、和集合は「記事に出てくる名前」として折りたたむ。文言は ui_copy_policy に従う |
| alert の重複 (`alert_dedup_gate`) | 本文 cos + pair ML | 候補記事が事象に入っていれば事象の根の一致、入っていなければ候補記事と事象の焦点の照合を特徴に足す (D で配管) |
| 遡及分割・統合を戻す | 状態の作り直し | 焦点も作り直す (`refresh_item_state` から `compute_focus` を呼ぶ) |

## 3 B — 統合を推移閉包でなく、事象の組を 1 つずつ判定する

### 3.1 流れ

```
候補の事象対 (今の記事対の索引・ML 承認・頻出名の追加辺で拾う。ここは変えない)
  → 事象対ごとに材料をまとめる (§3.2)
  → 焦点の照合で 4 値に分ける
       conflict → 結ばない (記録だけ)
       lineage  → F2 では止めない (F1b、§9.3)。関係 (系統) の候補として渡す。結ぶかは下の判定器
       weak     → 事象対の判定器を厳しいしきい値で
       support  → 事象対の判定器を通常のしきい値で
  → 結ぶ組を確信度の高い順に 1 つずつ処理 (§3.3)
       結んだら統合先の焦点を更新し、その事象に触れる残りの組を材料から作り直して判定し直す
  → 1 組 = 1 判断記録 (event_merge_decisions)
```

### 3.2 判定の入力 (焦点どうし)

| 材料 | 中身 |
|---|---|
| 焦点の照合 | 共有する焦点の名前 (型ごとの数)、CVE の食い違い、被害組織の食い違い、行為の組 (advisory × exploitation 等)、アクター名だけか |
| 錨どうしの確率 | 両側の seed 記事の組の pair ML の確率 (無ければ採点する。LLM 判定は fast、1 組 2.7 秒) |
| 支持記事どうしの確率 | 支持記事 × 支持記事の採点済みの組の平均・最大・被覆率 (相手のどれかと承認辺を持つ支持記事の割合)。**外れの記事の辺は数えない** = ハブに吸収された別件の記事が橋にならない |
| 要約埋込の重心 cos | 支持記事だけの重心 |
| 時間 | 両側の期間の隙間 (60 日の上限は今のまま辺単位で残す) |
| 大きさ・まとめ | 支持記事の数、まとめの事象か |

- **判定器 (正解ができるまで)**: 規則で置く。support = 今の規則 (辺 2 本、単独事象の救済) をそのまま。
  weak = 錨どうしの確率 ≥ 0.80 **かつ** 支持記事の被覆率 ≥ 0.5 (片側の焦点が空なら錨どうしの確率だけ)。
- **判定器 (正解ができた後)**: 事象対の 3 値分類器 (同一 / 系統 / 別)。関係の分類器 (09-27、AUC 0.88-0.89) と同じ型の RF。
  特徴は上の表。学習は E の事象対 200 組以上。しきい値は「同一」の適合率 95% を満たす点。

### 3.3 順序

1. 候補の組を **確信度の降順** (support → weak の順、同じ区分の中は錨どうしの確率、次に支持記事の被覆率) に並べる。
2. 先頭から処理。結ぶと決まったら:
   - 統合先 = 最初に立った事象 (URL が残る、今と同じ)。
   - 統合先の焦点を §2.2 の規則で更新。
   - その 2 事象に触れる残りの組を、更新した焦点で**照合し直す** (A–B を結んだ後の B–C は、A∪B の焦点と C の組として判定する)。
3. **1 回の実行で 1 事象が吸収するのは確信度の高い順に何件でもよい**が、各組が独立に判定を通ること。
   A–B・B–C が通っても A–C の照合が食い違いなら、C は結ばない (今の union-find なら結ばれる)。
4. 吸収側が 2 つの統合先の候補を持つ場合は、確信度の高い方だけ。もう一方とは関係 (系統の候補) として残す。

計算量: 30 日の候補の事象対は数千組、採点済みの記事対の確率は `event_pair_shadow` から読むので、追加の LLM は
錨どうしの組の未採点分だけ (毎時 数十組、予算 120 秒で打ち切り・持ち越し)。並べ替えと再照合は CPU で秒単位。

### 3.4 戻せること (10-22 の判断の記録・戻す操作との関係)

- 判断の記録は**今の 1 行 = 吸収された事象 1 つ**のままで、1 対ずつの判定と一致する (推移閉包では 1 行の根拠が
  「群のどこかの辺」だったが、今後は「この 2 事象の焦点の照合と確率」になる)。`focus_class` / `focus_json` を足す。
- 戻す操作は `eventnews_merge_undo.undo_merge` の 1 か所のまま。戻した後に焦点を作り直す処理を足す。
- **依存の扱い**: 戻した統合のあとに同じ統合先へ結ばれた統合は、焦点の育ちがその統合に依っていたかもしれない。
  `event_item_focus_log` の `decision_id` から、戻した統合で足された名前を**使って**通った後続の統合を列挙し、
  「要再判定」として次の毎時で照合し直す (自動では戻さない — 戻すのは照合が conflict になったものだけ、記録を残して)。

## 4 C — 群の中の点検と自動の分割

### 4.1 候補の選び方 (焦点の外れ)

- 毎日 1 回、生きている複数記事の事象について「外れ」(焦点と何も共有しない記事) を数える。
- 候補 = 外れが 2 件以上 **かつ** 支持記事を除いた割合が 20% 以上。直近 30 日の実データで
  **統合した事象 165 件中 10 件、毎時だけの事象 158 件中 1 件** (§8.5)。量は小さく、全組の採点が間に合う。
- 統合の判断の記録がある外れ (外れの記事が `retro_merge` で入った) は、分割ではなく**その統合を戻す**のを第一候補にする
  (戻せば元の事象・URL・本文が正確に戻る。分割は新しい事象を作る)。

### 4.2 切る判断

- 候補の事象の中で、**外れ × 支持記事** と **外れどうし** の組を全部採点する (pair ML + fast の LLM 判定、未採点の組だけ)。
  09-26 の検証の壁「群の中の組の観測率 0%」はここで埋める。
- 切るのは既存の `split.split_components` (承認辺の連結成分、t=0.70、09-02 の較正で群 P 100% / R 70%)。
  焦点は「どの事象を見るか」を選ぶだけで、切る判断には使わない (quorum 系は誤除去 8-24 で撤回済み)。
- **自動で実行する条件** (すべて満たす):
  1. 分離される成分が全部「外れ」の記事 (支持記事を 1 つも含まない)。
  2. 分離される成分の焦点と本体の焦点が **conflict** (CVE か被害組織の食い違い)。
  3. 分離される成分の記事が統合の判断の記録から来ていない (来ているなら undo を使う)。
- 上の条件を満たさない分割は**提案**として承認キュー (既存の運用画面の承認キュー) に出す。

### 4.3 誤った分割の害の抑え方

| 抑え | 中身 |
|---|---|
| 上限 | 自動の分割は 1 日 10 事象まで。超えたら残りは提案へ |
| 錨は動かさない | 本体 = 錨を含む成分 (最大成分ではなく)。URL と本文の主題が保たれる |

## 5 D — 同一性の判定を 1 つの部品に寄せる道筋

### 5.1 部品の形

`src/eventnews/identity/` (新しい package):

| module | 役割 |
|---|---|
| `inputs.py` | 判定の材料を作る**唯一の loader**: 記事の名前 (別名・法人格を畳む・伏字除外・頻出 cap を**記事の時期の** 14 日で数える)、本文埋込と要約埋込、種別 |
| `focus.py` | `compute_focus` (純粋関数) と焦点の照合 (`match_focus` → support / weak / conflict / lineage) |
| `article_pair.py` | 記事対の `same_event_proba(a, b)` (今の pair_model + pair_features を移す) |
| `event_pair.py` | 事象対の `event_link(e1, e2)` → 同一 / 系統 / 別 + 確率 |

### 5.2 どれを寄せ、どれを残すか

| 判定 (見直し §1.3) | 扱い | 理由 |
|---|---|---|
| 毎時の群化 | **寄せる** (記事 × 事象 = 記事対の確率 + 焦点の照合) | 統合と同じ問い |
| 統合・頻出名の統合 | **寄せる** (`event_link`) | B そのもの |
| 遡及分割 | **寄せる** (記事対の確率) | 既に judge_pairs を共有。材料の loader を揃える |
| 関係 (同じ出来事の系統) | **寄せる** (`event_link` の「系統」) | 定義の「系統」と同じ問い。同じアクター・包含は relations.py の規則に残す |
| alert の重複 | **寄せる** (事象の根の一致 → 無ければ `same_event_proba`) | 定義上「同じ事象 (続報を含む)」 |
| 続報の判定 (Discord の marker) | **寄せる** (事象の根の一致。cos 0.88 は撤去) | 修正 ⇔ 悪用を続報にしてしまう (食い違い #8) |
| 投稿直前の重複 | **残す**。ただし「事象の根の一致」を一致先の第一の根拠に足し、CVE の一致は種別が違えば重複にしない | 要約直後・群化の前に走り、速さと決定論が要る。群化の結果が無い記事が大半 |
| 取込前の重複 (hard / cluster / 同一バッチ) | **残す** | 要約の前で問いが違う (同じ記事の再配信か)。埋込の入力も要約前のものしか無い |
| 深掘りの時事性・台帳の塊化・高脅威ダイジェスト | **残す** (事象の根を読む消費者) | 判定ではなく読む側 |

### 5.3 寄せる順

1. `inputs.py` を作り、統合の段の入力 (種別・要約埋込・頻出 cap の時期) を毎時と同じ loader に揃える (T2・T3・T6 の受け皿)。
2. `focus.py` を A と同時に。
3. `event_pair.py` を B と同時に。関係の「系統」はその後 (relation_model の学習し直しと一緒)。
4. alert 重複・続報の判定を事象の根の参照へ (読む側の付け替え、各 1 PR)。
5. 投稿直前の重複に「事象の根の一致」を足す (残す判定の中の 1 規則として)。

一度に付け替えない。各段で「付け替えの前後で判定が変わった組」を記録し、変わった組だけを見る。

F2 (食い違いだけ止める) の 80 組での机上の適合率: 新しい定義で振り直したと仮定すると、正しい統合 62 のうち失うのは 1、
残る誤りは 2 (焦点が空の M2) → **61 / 63 ≈ 97%**。⚠ 18 組は設計に使ったので過大評価になりうる。

### 9.3 F1 の不合格と F1b の規則の修正 (2026-10-24)

F1 (conflict + lineage の本当に別 58%) の主因 3 つを直した。**記録の照合だけの変更で、統合・群化の判断は変えない**。
1. 被害組織の食い違い: 両側のどの組も同じ組織に読めるなら conflict にしない (別名判定 shadow の「同一」+ 緩い一致 =
   ひらがな⇔カタカナ・長音符・3 文字以上の接頭辞)。別名は conflict を**消す方向だけ**に使い、共有名に数えない (結合を増やさない)。
2. CVE の食い違い: 事象の記事 (支持 + 外れ) の過半が持つ CVE だけを根拠にする (`focus.trusted_names`)。
3. **lineage は F2 で止めない**: 照合の 4 値は残すが、`replay.STOPPING_CLASSES` は conflict のみ。lineage は
   `RELATION_CANDIDATE_CLASSES` として関係 (系統) の候補に回す (F2 の止める対象から外す)。

結果 (新標本 50 組、Opus 盲検): 新規則の conflict が本当に別 26/31 = 84% (67〜93%)。点推定は線 80% 超、区間下限は未達。

### 9.4 F2 の投入 (2026-10-24、利用者の §9.1-1 の線に基づく判断)

F1b の止めた組 (conflict) が本当に別 (different + lineage) 26/31 = 84% (区間 67〜93%)。点推定が線 (8 割) を超えたので

- **どこで効くか**: `merge.plan_merges` が「結ぶ条件 (辺の本数・単独記事の救済) を満たした事象の組」ごとに、統合前の両事象の

  lineage は**止めず**、関係 (系統) の候補として記録だけする。support・weak は今の判定のまま。
- **照合の入力は記録経路と同じ**: 別名判定 (`org_identity_pairs` の「同一」) を conflict を消す方向だけに渡す。判断記録の

  `action` = `blocked` (結ばなかった) / `shadow` (shadow で conflict だったが結んだ) / `relation_candidate` (lineage)。
  誤って止めた組は、この表で見つけて手で統合できる (統合の判断記録 `event_merge_decisions` は結んだ組だけなので、undo の経路と分かれている)。
- **既知の限界**: 照合は組ごとに独立。A-B と B-C が通れば A-C が conflict でも推移で結ばれる (設計 §3.3 の逐次処理は F5)。
  照合は適用前の事象の焦点で行うので、同じ回に A-B が結ばれた後の B-C を (A∪B) の焦点では見ない。
