# 情報要求の層 — 概念整理 (2026-09-15)

- 発端: 利用者「常設情報要求は PIR より上位の要求 (問い) にも思える。実装は急がないので
  概念の整理からしたほうがいい」
- 状態: **概念整理のみ。実装・改名は含まない** (決めるべきことは §5)
- 関連: [pir_system.md](pir_system.md) / [prepositioning_posture_ledger_design.md](prepositioning_posture_ledger_design.md) /

## 1. いま道具が持っているもの (名前 vs 実体)

| 呼称 | 件数 | 実体 | 答え (確度つき推定) を持つか |
|---|---|---|---|
| `mission` (pir.yaml root) | 1 行 | 任務文「日本標的の脅威を漏らさず検知する」 | — |
| **`pir_*`** | 20 | **主題 + 照合信号 + 重要度**。例「中国系 APT 動向」+ actors/countries + `target_importance: high` | **持たない** |
| **常設情報要求** (standing situation) | 4 | **問い**。例「中国の国家アクターは日本の重要インフラに対する事前配置を進めているか」 | **持つ** (claim / confidence / hypotheses / revision 197 件) |
| event situation | 216 | **事象の器** (報道された出来事の追跡単位) | 持つ (その事象についての判断) |
| `indicators` / `fired_indicators` | judgment の欄 | **指標 (I&W)** — 何が観測されたら判断が動くか | — |

`pir_*` の中身は「何を集め、何を重要とするか」の基準であって、疑問文ではない。
常設情報要求だけが疑問文で、しかも答えと軌跡を持っている。

## 2. doctrine の梯子と現状の対応

インテリジェンスの標準的な階層は **任務 → PIR (問い) → SIR (収集要求) → 指標 → 収集源**。
PIR は「指揮官の決定に紐づく問い」であり、答えを持ち、証拠で更新される。

| doctrine の層 | 本来の形 | 本道具での実装 |
|---|---|---|
| 任務 | 指揮官の任務 | yaml root の `mission` (1 行) |
| **PIR = 問い** | 「〜か？」= 決定に紐づく | **`pir_*` ではなく 常設情報要求 4 件がこれ** |
| SIR = 収集要求 | 何を集めれば答えられるか | **`pir_*` 20 件がここ** (signals + importance) |
| 指標 | 何が見えたら判断が動くか | judgment の `indicators` ✓ 正しい位置 |
| 収集源 | feed / scraper | `feeds.yaml` / `watchers.yaml` ✓ |

> **名前が 2 層ずれている。** `pir_*` は PIR ではなく SIR (収集主題)。
> 「常設情報要求」は "常設" が本質ではなく、**PIR そのもの** (常設なのはその属性)。

利用者の「PIR より上位の問い」という直観はこの位置ずれを指している。

## 3. ずれが生んでいる具体的な症状 (実測)

**(a) 問いが 4 件しかなく、全部 prepositioning。** 任務から導出されていない。
`pir_iran_apt` が存在しないのにイランの問いはある — **問いは `pir_*` から生えていない**ことの証拠。

**(b) 「PIR Coverage」は収集量を測っている。** `evaluator.compute_pir_kpi` が返すのは
match 件数 (7d/30d)・top feeds・trend。「その問いにいま答えられているか」は測っていない。
問いの層が無いので、測る対象が存在しない。

**(c) spotlight は主題ダイジェストであって回答ではない。** `pir_*` 単位の週次 narrative。
実測 (14 日): 候補記事が PIR ごとに 57-330 件と 6 倍違うのに key_events は 7.3-7.6 件で一定。
主題の要約だからこそ分量に反応しない。**問いへの回答なら、証拠量は確度を動かすはず**。

**(d) 状況総括の主役は事象。** judgment は事象単位で、問い単位の answer は常設 4 件だけ。
「今週、我々の問いに対して答えはどう動いたか」は報告の中心になっていない。

## 4. 先の「PIR へ統合」案は向きが逆だった

2026-09-15 の議論で「常設情報要求を PIR の一属性 (`standing: {...}`) にできないか」を検討したが、
これは**問いを収集主題の下に入れる**ことになり階層が反転する。
[prepositioning_posture_ledger_design.md](prepositioning_posture_ledger_design.md) §9-5
「PIR への判断状態の統合は採用しない」とも整合する — ただし §9-5 が却下したのは
「PIR に答えを持たせる」案であって、**宣言をどこに置くか**は別問題として未決のまま残る (§5-2)。

正しい向きは「`pir_*` の**上**に問いの層を置く」。問いは答えを台帳に持ち、`pir_*` は
収集・評価の基準のままでよい。

## 5. 決める必要があること (未決)

1. **問いの層を一級市民にするか。** 今は「常設情報要求」という名前で 4 件だけ存在し、
   prepositioning という 1 つの型に縛られている。任務から問いを起草する運用にするなら、
   型 (ACH フレーム + 収穫規則) を複数持てる必要がある。
2. **問いは誰が書くか。** 現在はコード所有 (`STANDING_SEEDS`、増減はレビュー)。
   運用 config は DB が SSoT という原則 (CLAUDE.md §12) とは不整合だが、問いには
   専用の機構 (仮説フレーム・収穫規則) が紐づくため単純な data 化はできない。
   分け方の候補: **問い文と国はデータ (DB)、フレームと収穫規則はコード (enum で選択)**。
3. **問いごとの機構をどう供給するか。** 現行の `POSTURE_HYPOTHESES` は
   prepositioning 専用で、event 用の仮説 union からは意図的に除外されている。
   別の型の問い (例: 「アクター X の能力は向上しているか」) には別フレームが要る。
4. **呼称を doctrine に寄せるか。** `pir_*` → 収集主題 への改名は config key /
   API path (`/api/v1/pir`) / DB key / UI 文言に波及する。
   **概念の分離と改名は別の決定** — 概念だけ先に固め、改名はしなくても運用できる。

## 6. 改名しなくても今日から効く指針

- **新しい「問い」を足したくなったら、それは `pir_*` ではなく常設情報要求の側**。
  `pir_*` を増やしても答えは生まれない (収集と重要度が変わるだけ)。
- **`pir_*` に「答え」を持たせようとしない** (§9-5)。答えの器は台帳。
- **「問いの被覆」と「収集の被覆」を別々に語る。** 現行の PIR KPI は後者。
  前者を測りたいなら、常設情報要求の確度と鮮度がその指標になる。
- 報告の幅を絞るとき、**常設情報要求は上限から除外する** (実装済み)。
  静かな週ほど salience が下がるため、機械的に絞ると最も見えているべき週に消える。
