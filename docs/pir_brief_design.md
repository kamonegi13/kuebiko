# PIR ブリーフ / SIR ブリーフ の分離 — 設計 (2026-09-15)

- 発端: 利用者「PIR ブリーフと SIR ブリーフで分けたほうがいい。ただし **PIR ブリーフは
  日・週・月の範囲で個別に出すものではなく、過去から現在に至るまでの状況を総括して
  問いに日々答える**形になるのではないか」
- 上流の概念整理: [intelligence_requirements_layering.md](intelligence_requirements_layering.md)
- 状態: **設計。実装なし** (未決は §7)

---

## 0. 要約 (BLUF)

現行の配信物はすべて **期間の産物** (この窓で何が起きたか) である。しかし
**問いへの答えは状態であって期間の産物ではない** — 「中国は日本の重要インフラへの事前配置を
進めているか」の答えは、24 時間の出来事ではなく**これまでに知り得たすべて**から導かれる。

> **SIR ブリーフ = 期間の産物**「この窓で何を集め、何が起きたか」
> **PIR ブリーフ = 状態の産物**「いま、問いにどう答えるか。前回の答えから何がどう動いたか」

この分離は新しい保存層を要しない (§5)。台帳が既に状態と軌跡を持っているため、
PIR ブリーフは**台帳の射影**として成立する。成立を妨げるのは**問いの数と型**だけ (§6)。

## 1. 何が違うのか

| | SIR ブリーフ | PIR ブリーフ |
|---|---|---|
| 主語 | 事象・収集 (what happened) | **問い** (what do we now believe) |
| 時間 | 窓で区切る (24h / 週 / 月) | **区切らない**。「◯月◯日時点の答え」+ 前回答えからの差分 |
| 記録の鍵 | `(period_type, period_start)` | **問い (situation_id) × 版 (rev)** — 既存 |
| 変化の意味 | 今期に起きたこと | **答えが動いたか** (動かなければ「動かなかった」と書く) |
| 静穏時 | 「本期間は事象が少なかった」 | **「答えは動いていない。ただし鮮度は◯日、開いている指標は N 件」** |
| 読者の問い | 何が起きた? | で、結局どうなんだ? |

**期間で切れないことが本質**。状態を窓に分解しようとすると、週次の軌跡射影
(判定 92 件を 1 報告へ) のような無理が生じる — 2026-09-15 に幅の改修で扱った症状は
この無理の表面化でもあった。

## 2. 現行の配信物の再配置

| 現行 | 実体 | 新しい枠組みでの位置 |
|---|---|---|
| **PIR daily focus** (朝刊 ②) | `pir_*` ごとの直近 24h マッチ集約 | **SIR ブリーフそのもの** — 既に存在する |
| **事象ニュース** (event news) | 事象単位の記事 | SIR の下 = 収集物の提示 |
| **状況総括** (synthesis、朝刊 ①) | 台帳判定の**期間射影** | **宙ぶらりん**。台帳 = 状態を持ちながら窓で切っている |
| **spotlight** | `pir_*` ごとの週次 narrative | SIR ブリーフの週次版 (主題ダイジェスト) |
| **JP CI board の posture カード** | 常設 4 問の現在推定 | **PIR ブリーフの原型** (ただし問いが tooltip、国名が見出し) |

状況総括の中身は 2 種類が混ざっている:

- **事象単位の判定 (216 situation)** → SIR 側 (収集した事象の評価)
- **常設情報要求 4 件の答え** → PIR 側

→ 分離後、**2026-09-15 に議論した「報告の幅」は SIR ブリーフ側の話**になる
(事象をいくつ本文に載せるか)。PIR ブリーフの幅は「問いの数」で決まり、salience で
絞る対象ではない (問いは全部答える)。

## 3. PIR ブリーフの形

問い 1 件あたりの単位 (材料はすべて既存 — §5):

```
問い       中国の国家アクターは日本の重要インフラに対する事前配置を進めているか
現在の答え  世界では観測されるが日本向けの証拠は無い
確度       低 (ACH=low / source_basis=news / 帰属の強根拠なし)
前回から    後退 — ◯◯の証拠が反証された (9/12)
根拠       直接 (JP) 0 件 / 関連 12 件 (30 日)
変われば    [指標] 国内 CI セクタへの帰属済み侵入が 1 件でも観測される (未発火)
           [指標] ◯◯の doctrine 文書の改訂 (9/10 発火)
鮮度       最終証拠 9/14 (2 日前)
```

配信の形 (推奨、§7-3 で要決定):

1. **動いた問いを先頭**に、変化の理由つきで
2. **動かなかった問いは 1 行**で現状 + 鮮度 (省略しない — 「静か≠安全」の明示)
3. 冒頭に「本日、N 問中 M 問の答えが動いた」

実測 (常設 4 問、65 日): 再評価は 0.48-1.17 回/日、そのうち答えが動くのは 15-55%。
cn は約 6 日に 1 回、ru は約 2 日に 1 回動く。確度自体も low/moderate/high を行き来している
(4 問すべてで 2-3 段階)。**毎日出す価値のある変化量はある**。

## 4. SIR ブリーフの形 (現行からの差分)

現行の朝刊 ② (PIR daily focus) をそのまま SIR ブリーフとし、状況総括の事象判定部分を
ここへ寄せる。差分は主に**位置づけの明示**:

- 「これは収集の報告であって、問いへの答えではない」ことが読者に分かる構成
- 収集の被覆 (どの主題に何件届いたか) を一級の情報として扱う
- 幅の設計 (2026-09-15 実装済み: 重要度基準 + 一覧 + 件数) はこちらに属する

## 5. データモデルへの含意 — 新しい保存層は要らない

PIR ブリーフに必要な材料はすべて既存:

| 要素 | 既存の所在 |
|---|---|
| 問い | `STANDING_SEEDS[].title` (将来は DB、§7-2) |
| 現在の答え | `situation_revisions.claim` + `leading_hypothesis` (最新 rev) |
| 確度と根拠 | `confidence` + `confidence_basis` |
| 前回からの変化 | `delta_type` + `delta_note` |
| 何が見えれば変わるか | `situation_forecasts` (3,383 件、open→scored の lifecycle) |
| 鮮度 | `situations.last_evidence_at` |

**PIR ブリーフは台帳の射影**であり、`status_synthesis` のような窓キーの保存を持たない。
「配信済みかどうか」だけは要る (前回配信以降の差分を出すため) — 既存の
`posted_at` と同型の軽い記録で足りる。

## 6. 成立の前提条件

**問いが 4 件では PIR ブリーフは成立しない。** 現状は prepositioning 1 型 × 4 カ国のみで、
任務 (「日本標的の脅威を漏らさず検知する」) に対する問いの網羅からは程遠い。

必要なもの:

1. **問いの起草** — 任務から問いを導く運用。単発の問い (分析チャット) の記録と昇格が
   自然な入口 ([intelligence_requirements_layering.md](intelligence_requirements_layering.md) §3-e)
2. **問いの型 (フレーム)** — `POSTURE_HYPOTHESES` は prepositioning 専用。別の型の問い
   (例「アクター X の能力は向上しているか」「セクタ Y の露出は悪化しているか」) には
   別の仮説フレームと収穫規則が要る
3. **問いの所有者** — コード所有 (現行) か DB か。候補: **問い文はデータ、フレームはコード (enum)**

## 6b. 配信物の全体像 — 窓と頻度を一致させる

1/2/3 を個別の選択肢として扱うと現状の混乱を固定してしまう (利用者指摘)。
3 つは 1 つの再編の断片なので、**目標形を先に決めてから順序を導く**。

### 貫く原則

> **流入 (flow) の器は「窓 = 配信間隔」。状態 (state) の器は窓を持たない。**

窓と配信間隔がずれると、器は流入でも状態でもなくなる。

### 現状の適合

| 器 | 窓 | 配信 | 判定 |
|---|---|---|---|
| PIR daily focus | 24h | 日次 | ✓ 整合 (流入) |
| 事象ニュース | 事象 | 随時 | ✓ 整合 |
| **spotlight** | **8 日** | **日次** | **✗ ずれ** |
| **状況総括 (daily/weekly/monthly)** | 窓あり | 同間隔 | ✗ **中身が状態** (台帳) — 状態を窓で切っている |

**spotlight のずれの実測 (2026-09-15)**: 連日の key_events の重なりは **中央 40%**
(完全一致 5/119、重なりゼロ 12/119)。8 日窓を日次で作り直すため、毎日 4 割を再掲している。
さらに窓の重なりは構造上 7/8 = 約 87% なのに内容の重なりが 40% しかない = **日々の差分の
大半は新着ではなく選抜のブレ** (LLM 直接選抜の非再現性、SYNTHESIS §33 と同型)。

### 目標形

| 器 | 種類 | 窓 | 配信 | 中身 |
|---|---|---|---|---|
| **PIR ブリーフ** | **状態** | **なし** | 日次 | 問いへの答え・確度・変化・指標・鮮度 |
| **SIR ブリーフ** | 流入 | 24h | 日次 | 主題ごとに何が届いたか |
| SIR 週次 (任意) | 流入 | 7d | **週次** | 週の流入まとめ (窓=頻度) |
| 事象ニュース | 事象 | 事象 | 随時 | 事象単位の記事 |

### 現行物の行き先

| 現行 | 行き先 |
|---|---|
| PIR daily focus | **SIR ブリーフ本体**へ (ほぼそのまま) |
| 状況総括 の事象判定 (216) | **SIR 側**へ (2026-09-15 の幅の設計はここに属する) |
| 状況総括 の常設 4 問 | **PIR ブリーフ**へ |
| 状況総括 weekly/monthly | **未決** (§7-1) — 流入の週次まとめとして残すか、PIR ブリーフの長期軌跡へ畳むか |
| spotlight の key_events (流入の選抜) | SIR 週次へ (窓=頻度に直す) か、24h の SIR ブリーフへ畳む |
| spotlight の outlook (4 観点の見通し) | **PIR ブリーフ**へ — 見通しは問いの機能であって主題の機能ではない |
| spotlight の caveats / unknowns | 両方に要る (流入にも状態にも留保はある) |

**「1 が本筋、3 が暫定」ではなく、3 は 1 の帰結**である。spotlight を畳む/週次化する
判断は、outlook の行き先 (= PIR ブリーフ) が用意できて初めて損失なく実行できる。

### 順序 (依存関係)

```
段A  PIR ブリーフの面を作る (既存 4 問・既存データのみ)
      ↓ 問いが器として成立することを確認
段B  問いを増やす (型を 1-2 個追加 + 起草経路)
      ↓ outlook の行き先ができる
段C  spotlight を再配置 (outlook → PIR ブリーフ / key_events → 窓=頻度へ)
      ↓ 主題ダイジェストが 1 本になる
段D  状況総括を分解 (事象判定 → SIR / 常設 → PIR) + 週次月次の去就を決める
```

⚠ **段C は SFT の評価面を壊す**。spotlight の尾部欄 (caveats/unknowns) は narrative
モデルの合否線そのもの (30 層の採否はここで測った)。学習・評価の系列が一段落してから着手する。

## 6c. 問いの型 — 何が型を構成し、どこまでユーザの問いに対応できるか

利用者「複数の型の候補を考察した上で、ユーザの問いに対応できるようにしておく必要がある」。

### 型 = 3 つの部品

| 部品 | 現行 (posture 型) | 所有 |
|---|---|---|
| **競合仮説の集合** | `POSTURE_CORE` 3 件 + `SHARED` (報道アーティファクト等) | コード |
| **証拠の適格条件** | R1-R3 の手書き規則 (intent × nation × CI セクタ × JP victim) | コード |
| 再評価の引き金 | 予約枠 + staleness 7 日 | コード |

**「型を増やすのが高い」の実体は 2 番目**。仮説は 3-4 件の文章なので安い。
証拠条件が手書きだから高い。

### 証拠条件は既に宣言文法がある

routing / PIR が共有する `match` ツリー (all/any/not + 葉 `{property, op, value}`) が既にあり、
`PROPERTY_CATALOG` は **日本関連フラグ (japan_critical / japan_relevant / llm_japan_targeted)、
ゼロデイ、既知 APT 言及、article_type、importance、category、victim_sector、actor_nation、
keyword_list、max_cvss** を持つ。

posture の R1-R3 を照らすと:

| 規則 | 必要な property | 現行カタログ |
|---|---|---|
| R1 intent=prepositioning かつ 国一致 | `intent`, `actor_nation` | **`intent` が無い** |
| R2 intent∈(espionage,disruption) かつ 国一致 かつ CI セクタ | `intent`, `actor_nation`, `victim_sector` | 同上 |
| R3 victim_country=JP かつ CI セクタ かつ 国一致 | `victim_country`, … | **`victim_country` が無い** |

→ **`intent` と `victim_country` をカタログに足せば、R1-R3 は宣言文法で書ける**。
そうなると証拠条件はデータ (UI 編集可) になり、**型の増設コストは仮説 3-4 件の記述だけ**に落ちる。

⚠ ただし [prepositioning_posture_ledger_design.md](prepositioning_posture_ledger_design.md) §9-3 が
「汎用 assignment matcher への相乗り」を却下している (国 anchor による戦線バケット吸着)。
却下されたのは **situation への割当**であって `match` 文法ではないが、
同じ事故 (粗い国一致で無関係な記事を吸う) を招かないよう、**証拠条件は割当より厳しい**
ことを型の要件にする必要がある。

### 型の候補 (問いの形は少ない)

| 型 | 問いの形 | 仮説の骨格 | 状況 |
|---|---|---|---|
| **A 存在・進行** | 〜は進行しているか | 進行中 / 他所で進行・当地に証拠なし / 別動機 | **実装済** (posture、4 問) |
| **B 帰属** | 誰がやったか | アクター候補 + 未帰属 + 誤報 | **実装済** (`CYBER_CORE`) だが**事象に付いており問いになっていない** |
| **C 意図** | なぜやっているか | 諜報 / 妨害 / 威圧 / 金銭 … | **実装済** (`GEO_CORE`) 同上 |
| **D 能力** | 〜できるようになったか | 実証済み / 主張のみ / 能力なし / 不明 | 未。実証と主張の区別が肝 |
| **E 趨勢** | 〜は悪化しているか | 悪化 / 横ばい / 改善 / **観測バイアス** | 未。⚠ 下記 |
| F 露出 | 我々は晒されているか | — | **不可** — FFIR = 自分側データを持たない |
| G 予測 | 〜は起きるか | — | **禁止** — 「外挿/予測しない」の確定原則 |

⚠ **E (趨勢) は「収集量を重要性の代理にしない」(CLAUDE.md §7) が直撃する**。
記事が増えたのは活動が増えたからか収集網が広がったからか区別できない。
採用するなら **「観測バイアス」を一級の競合仮説として必ず立てる**ことを型の定義に含める。

### ユーザの任意の問いに対応できるか — 否、そして否でよい

**すべての問いが常設情報要求になれるわけではない。** 資格要件:

1. **競合仮説が立つ** — 答えが 2 つ以上の排他的な見立てに割れる
2. **証拠の適格条件が宣言的に書ける** — どの記事がこの問いの証拠かを機械判定できる
3. **答えが時間で動きうる** — 動かないなら台帳に置く意味がない
4. **予測でない** (原則 G)
5. **自分側データを要しない** (原則 F)

要件を満たさない問いは**単発 (RFI) のまま**扱う。作るべきは大きな型のライブラリではなく
**この資格判定**であり、通った問いを型へ写像する経路である。

そして重要な帰結: **型は 5 つで足り、多様性は主語が担う**。
「中国は日本 CI へ事前配置を進めているか」と「北朝鮮は韓国金融へ…」は同じ A 型で主語が違うだけ。
型を無限に増やす必要はない。

## 6d. 穴埋め (文型 + スロット) — その像で正しい。ただし現行は穴埋めが保護されていない

利用者「各型に穴埋めで主語、目的語などを入れていくイメージでしょうか」。**そのとおり**で、
現行の posture 型は既に**スロット 1 個 (国) のテンプレート**である:

```
「{国} の国家アクターは日本の重要インフラに対する事前配置を進めているか」
```

### ⚠ ただし穴埋めの結果が上書きされている (2026-09-15 実測)

| seed (コード) | いま台帳にある問い |
|---|---|
| 中国の…事前配置を進めているか | ✓ 変化なし |
| **北朝鮮**の…事前配置を進めているか | ✗「北朝鮮の国家アクター(Kimsuky等)は**韓国の金融文書**を装った LNK ファイル等で情報窃取を行う新手法を運用しているが…」 |
| **ロシア**の…事前配置を進めているか | ✗「ロシアの国家アクター(APT29/Cozy Bear系の…UNC6293・UNC7005・UNC5976等、および別系統の…」 |
| **イラン**の…事前配置を進めているか | ✗「イランの国家アクター(IRGC関連含む…)は**英国・米国等の西側**重要インフラ…」 |

原因は `stateful.py` の同一性追従 — 「評価済み claim が title と乖離したら title を進める」
(`update_title`)。**event situation では正しい** (続報で事象の輪郭が定まる) が、
**常設情報要求では誤り**: 問いは固定で、動くのは答えだけ。LLM の claim は**答え**なのに、
それを**問い**に上書きしている。

被害:
1. **問いが失われた** — kp は「日本の重要インフラ」という主題を丸ごと落として韓国金融の話になった
2. **答えが問いを汚染し続ける** — 増分 ACH は「前回判定 + 新着」で評価するため、ずれた問いを
   前提に次の評価が乗る
3. **UI で見えない** — posture カードは見出しが国名・本文が仮説ラベルで、問いは tooltip (§3b)

→ **構造要件: 問い (文型 + スロット値) は不変。答えだけが動く。** event と standing の非対称。

### スロットの語彙は既存の SSoT 辞書から取る

| 型 | 文型 | スロット (語彙の出所) |
|---|---|---|
| **A 存在・進行** | {主体} は {対象} に対して {行為} を進めているか | 主体=国/アクター (`STATE_NATIONS` / actor 辞書)、対象=国×セクタ (`countries.yaml` / `victim_sectors.yaml`)、行為=intent (`diamond_model`) |
| **B 帰属** | {事象/キャンペーン} の背後にいるのは誰か | 事象=situation、候補=actor 辞書 |
| **C 意図** | {主体} の {活動} の目的は何か | 主体=アクター、活動=intent 軸 |
| **D 能力** | {主体} は {能力} を獲得したか | 主体=アクター、**能力=語彙が無い** — MITRE ATT&CK technique (`mitre_sync` 済) が候補 |
| **E 趨勢** | {対象} に対する {脅威種別} は悪化しているか | 対象=国×セクタ、脅威種別=`category` / `article_type` |

**これが穴埋め方式の本当の利点**: スロットが照合器と同じ語彙 (actor_nation / victim_sector /
intent / victim_country) から来るなら、**穴を埋めた時点で 3 つが同時に決まる**:

1. **問い文** — 文型にスロット値を差し込む
2. **証拠の適格条件** — スロット値がそのまま match ツリーの葉になる (§6c の R1-R3 は
   A 型に (国=cn, 対象=JP×CI, 行為=prepositioning) を入れた結果と一致する)
3. **仮説文** — 骨格の {対象} 等にスロット値を差し込む (「日本 CI への事前配置が進行中」)

→ ユーザは**語彙から選ぶだけ**で新しい問いを作れ、コード変更が要らない。
語彙が SSoT で統制されているため、§9-3 の吸着事故 (粗い国一致で無関係を吸う) も起きにくい。

### 残る穴

- **D 型の「能力」語彙**が無い。ATT&CK technique を使うなら、既存の `mitre_sync` が
  そのまま SSoT になる (辞書は既にある)。
- **文型ごとの仮説骨格**はコード所有のまま (3-4 件の文章)。ここは増設が安いので問題ない。
