## 0. 最初に確かめたこと (台帳の注記の宿題)

1. **本番で前選びの ML は効いていない** (読むだけで確認): `src/digest/deep_dive_selector.py:_ml_prefilter` は
   `DEEPDIVE_ML_PREFILTER` (本番は未設定 = 既定 90) 件より候補が少なければ素通しする。本番の候補は上流の
   決定論の関門 A で 60 件に切られてから届く (`run_logs` の `deep_dive_prefilter_done` の `after_cap: 60`、
   10-18・10-25 の run)。`deep_dive_ml_prefilter` のログは `run_logs` の保持範囲 (09-29〜) に 0 行。
   よって「今」= 関門 A の 60 件 → LLM の採点、で ML は使われていない
2. **判定集の判定者**: `data/mlx/deep_dive_goldset.jsonl` の行に判定者の欄は無い。作成スクリプト
   (`scripts/build_deep_dive_goldset.py`) の既定は `claudecode:sonnet`。Opus かどうかはファイルからは確かめられない。
   以下では「LLM 審判 (判定者不明、腕とは独立)」として扱い、報告に明記する
3. **「12」の意味**: 判定集 470 行・13 窓に「12」に当たる単位は無い。`data/mlx/frozen_deep_dive.json` の
   3 窓 × 12 件 (11 件) は本番の LLM の選定の凍結で、Opus の選定ではない。id の「12」は判定集の実体を指さない

## 1. 仮説

関門 A (決定論、60 件) の代わりに ML の予測上位 60 件を LLM の採点に渡しても、LLM の選定 (上位 K 件) と
審判の「深掘りの対象」との一致は下がらない (「現行以上」)。

## 2. 母集団

- 候補: `data/mlx/deep_dive_labels.jsonl` の 13 窓 × 180 件 (window_end 06-22〜09-14)。各行に LLM rubric の
  `composite` (全行あり) と関門 A に入ったか (`in_gate_a`、窓ごとに 60 件) がある
- 判定する行: 判定集 `data/mlx/deep_dive_goldset.jsonl` の 470 行 (候補の部分集合、層 selected 144・
  near_miss 118・random 179・targeted 29)。正 = `urgency ≤ 1` かつ `need_to_know ≥ 2`
  (作成スクリプトの定義「深掘りの対象 = urgency 低 × need_to_know 高」)
- 除外して数える: 判定集の行が候補に無い、特徴量の行と composite が食い違う (§5.1 の照合)

## 3. 期間と分割 — leave-window-out を採る

- **採用: leave-window-out (13 回の学び直し)**。窓 w の判定には、w を除く 12 窓の候補で学び直した Ridge
  (本番と同じ: StandardScaler + Ridge(alpha=1.0)、目的変数は composite) を使う
- 理由: 本番のモデルが学習していない窓は 3 (08-31・09-07・09-14、判定行 132) しかなく、窓単位の符号検定は
  3 窓では最小の p 値が 0.25 で何も言えない。13 窓なら全勝で p = 0.0002 まで出せる。学び直しの目的変数は
  LLM の composite で判定集のラベルではないので、判定集のラベルは学習に入らない
- 代償 (報告に書く): 過去の窓の判定に未来の窓を学習に使う (時間の向きの漏れ)。そこで**副解析**として
  本番のモデル (`config/models/deep_dive_model.json`、10 窓で学習) を学習外の 3 窓にだけ当てた結果を併記する
  (合否には使わない)
- R18: 窓 w の判定行の記事と同じ閉包 (§7) に入る記事を、w の学び直しの学習から外す (同じ記事が別の窓にも
  候補として現れる場合を含む)

## 4. 標本と重み

  一致率は母集団の率ではなく**腕の比較のための対の指標**として読む

## 5. 腕と検定

### 5.1 入力

- 特徴量: `data/eval/z2_deep_dive_input.npz` (`X_large`、2,340 × 54、`scripts/train_deep_dive_ml.py` の
  `build_matrix` で 10-11 に作った凍結)。行の順はラベルのファイルの順。**各行の `y_cont` がラベルの composite と
  一致することを全行で照合**し、1 行でも食い違えば実行しない
- 特徴量の列名が `DD_FEATURE_NAMES` と一致することを照合する

### 5.2 両腕 (窓ごと)

- **今 (A)**: プール = `in_gate_a` の 60 件 → composite の上位 K
- **ML (B)**: プール = 学び直した ML の予測の上位 60 件 (180 件から) → composite の上位 K
- 同点は article_id の昇順で決める。K = 40 (本番の `DEFAULT_MAX_SELECT`) を主、K = 20 を副
- 感度 (合否に使わない): ML のプールを 90 件 (本番の既定の k) にした B90

### 5.3 指標と検定

- 窓 w・腕 X の一致数 agree_w(X) = 判定行のうち「X が選んだ」と「正」が一致する行の数
- 主検定: d_w = agree_w(B) − agree_w(A) の符号検定 (正確な二項、差 0 の窓は除く)、13 窓
- 副: 行単位の McNemar の正確検定 (全窓を合わせる)、腕ごとの選定の適合 (選んだ判定行のうち正の割合)・
  回収 (正の判定行のうち選んだ割合)

## 6. 合否の線 (結果を見る前に固定)

- **現行以上 (合格)**: Σ_w d_w ≥ 0 **かつ** 「B が劣る」向きの片側の符号検定で p ≥ 0.05
- **劣る (不合格)**: 上のどちらかを満たさない
- B が勝つ向きの片側 p < 0.05 なら「現行より良い」と書き添える
- 判定集のラベルの判定者が確かめられない (§0.2) ことは結論に必ず併記する
- 本番の前選びは今 0 回しか効いていないので、合格でも「ML を足す価値がある」までは言わない (関門 A の置き換えで
  同等、と書く)
