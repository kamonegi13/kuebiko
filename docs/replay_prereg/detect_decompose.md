## 2. 母集団

### 2.1 窓 (入力の単位)

- 窓 = **UTC の 6 時間の区間** (00-06・06-12・12-18・18-24)。範囲は事象時刻 `[2026-10-27T00:00Z, 2026-11-04T00:00Z)` の 32 区間
  (範囲の終わりは固定。GPU-B の開始が遅れても延ばさない)
- 窓の入力 = その区間に `articles.created_at` が入り `status='posted'` かつ importance high/medium の記事を、
  追跡中の情勢への割当の後の残余 (`already = assigned_article_ids()` と `match_situation` の後、
  v6 の教師で直した型) にし、detect ML で `scripts/replay_detect_prefilter.py` の `narrow` と同じ規則 (top-K=本番値・勧告除外・high の下限保証) で絞った候補
- 追跡中の題名 = **窓の開始時刻より前に開いた情勢** (`select_active_as_of` の型。まだ無い情勢を告げない)。
  本番と同じ埋込の絞りを掛ける
- 窓の入力は両腕で**同一のスナップショット**を使う: 実行前に全 20 窓の入力 (候補の記事 id・題名・要約・追跡中の題名・種別) を
  `inputs.json` に固定し、sha256 を manifest に残す。腕ごとに DB から取り直さない (対にするため)
- 除外して数える欄 (各件数を報告に書く): (1) 候補が 5 件未満の窓 (空の窓で差が出ないため)、(2) 追跡中の題名が 0 件の窓、
  (3) 入力の記事が DB から読めない窓、(4) R18 の除外 (§7)

### 2.2 開設の単位 (裁定の単位)

- 1 つの腕の 1 回の run が開いた claim = (腕, 窓, run, 記事 id の集合, claim 文)。裁定の単位は
  **(腕, 窓, 記事 id の集合, claim 文) の完全一致で畳んだ**もの (3 回で同じなら 1 単位。同じ記事の集合でも claim 文が違えば別の単位)。
  記事の集合の一致は集合として比べ、順序は無視する

## 4. 標本と重み

- 窓の抽出: §2.1 の 32 区間から §2.1 の除外 (1)(2)(3) を引いた適格な窓を、区間の開始時刻の昇順に並べ、
  `random.Random(20261104)` で shuffle し、**先頭から 20 窓を取る。ただし同じ UTC 日からは最大 3 窓** (3 窓目まで取った日の窓は読み飛ばす)。
  適格な窓が 20 未満なら**あるだけ使い**、18 未満なら「判定不能」(§6)
- 重み: 各窓の重みは等しい (台帳の weighting: 窓で層化・各窓の重み等しい)。層 = UTC 日。層ごとの n は 1〜3 と小さいので、層別の値は区間を付けず**参考として出すだけ**
- 各窓 × 各腕を **3 回** (run) 走らせる。run の間は本番と同じ温度 (乱数種は固定しない = 本番の揺れを含める)。
  腕の順序は (窓, run) ごとに `random.Random(20261104 + 窓の通し番号 * 10 + run)` で入れ替える (ホストの温度・キャッシュの偏りを避ける)
- Opus の裁定の標本: 畳んだ単位 (§2.2) の総数を U とする。**U ≤ 260 なら全数**。U > 260 なら、層 = (両腕に出た / 現行腕だけ / 出荷腕だけ) の
  3 層に比例配分して 260 を `random.Random(20261104)` で抜く (単位の id の昇順に並べてから shuffle)。重みは層の U / 抽出数。
  抜かれなかった単位は「未裁定」として数え、その単位の claim は指標の分子・分母から重みで補う
- 裁定の残り 40 回は 2 回目の独立な裁定に使う (一致率と κ の報告用、無作為に 40 単位を同じ乱数で選ぶ)。合計 Opus 300 回 (台帳の `opus: 300`)

### 5.2 裁定 (盲検)

- 付け手は新しい文脈の Opus。渡すもの: 単位の claim 文、束ねた記事の見出し・要約・公開日 (窓の終わりの時刻まで)、
  窓の開始前に追跡中だった情勢の題名一覧。**渡さないもの**: 腕の名前、モデル名、確率、run 番号、他の単位。単位の提示順は乱数で入れ替える
- 問い (3 つ、`docs/event_identity_definition.md` の定義):
  - Q1 追跡中の情勢と**同じ事象でない**か (同じ事案の続報 = 同じ事象)
  - Q2 追跡する価値があるか (続報で見立てが動きうる = trackable。制裁発表・解体・統計・衛星画像分析の単発は否)
  - Q3 claim が見出し・要約の範囲内か (見出しに無い属性・格上げ・複数文を足していない)
- **正しい開設 = Q1 ∧ Q2 ∧ Q3 がすべて「はい」**。**誤った開設 = 1 つでも「いいえ」**。判断不能は単位の外へ (件数を報告)
- 裁定は `data/eval/adjudication_ledger.jsonl` に記録 (R23、同時に走らせる裁定は 1 本)

### 5.3 指標と検定

- 窓 w・腕 a・run k ごとに C = 正しい開設の数、W = 誤った開設の数。窓ごとの腕の値 = 3 回の平均
  (その窓のフォールバックの run は平均から除く。3 回すべてがフォールバックなら窓を出荷腕の欠測にし、対から外す)
- 主指標: 窓ごとの差 d_w = (C−W)_出荷 − (C−W)_現行
- **Wilcoxon の符号順位検定** (両側、引き分け = d_w=0 を除く)、符号検定 (引き分けを除く、両側) を併記
- 区間: **窓の cluster bootstrap 2,000 回** (窓を復元抽出、百分位 95%、乱数種 20261104)
- 誤開設率 = Σ W / Σ (C+W)、腕ごとに窓を cluster とする重みなしの合計比。差の区間も同じ bootstrap
- 多重比較: P1〜P5 は**すべて満たして合格** (積集合の検定なので補正しない)。Wilcoxon は P1 の拒否権としてのみ使い、他は記述

## 6. 合否の線 (結果を見る前に固定。すべて満たして合格)

- **P1 (主、非劣性)**: d_w の平均の bootstrap 95% 区間の**下限 ≥ −0.5 (窓あたり)**。かつ Wilcoxon が「出荷腕が有意に悪い」でない
  (p < 0.05 かつ d_w の中央値 < 0 のとき不合格)
- **P2 (誤開設率)**: 誤開設率の差 (出荷 − 現行) の bootstrap 95% 区間の**上限 ≤ +5 点**
- **P3 (関門の止めすぎの歯止め、11-03 改訂)**: 出荷腕の全 run の「裏付けの関門で止めた claim の数 (`n_gate_blocked`)」/「開いた claim + 止めた claim」の割合の点推定 **≤ 0.20**。分母が 30 件未満なら「判定不能」。あわせて、開いた claim を `claim_grounding.check_grounding` に当てた違反率 (構造上 0 の見込み) と Opus の Q3 が「いいえ」の割合を参考に出す (判定には使わない)
- **P4 (出荷腕の健全性)**: 出荷腕の全 (窓, run) のうち分けた形が適用された割合 **≥ 90%**。下回れば「判定不能」
  (分けた形を判定していないため。不合格にも合格にもしない)
- **P5 (開設数の歯止め)**: 出荷腕の開設数 (畳む前) の合計 / 現行腕 **≤ 1.5**
- **判定不能の条件**: 窓が 18 未満 / P3 の分母が 30 未満 / P4 が 90% 未満 / 裁定できた単位が U の 80% 未満 / 実行の前提 (§9) を満たさない。
  判定不能は合格ではない。SW-DETECT は出さず、調整役へ戻す
- 1 つでも不合格なら不合格。不合格のときは、本書の中で線・母集団を変えて再判定せず、新しい標本で prereg からやり直す

### 調整役の決定 (台帳が決めていなかった点を、最も保守的に本書で固定した)

1. **窓の定義**: 台帳は「窓 (日)・20 窓は 10-27 以降から無作為」だが、10-27 から GPU-B の前日までは約 8 日で、日単位では 20 窓にならない。
   → 窓を UTC 6 時間の区間にし (32 区間)、同じ日から最大 3 窓。区間は重ならない (24h の本番の窓を重ねると窓が独立でなくなるため)。
   代償: 窓の候補が本番の 24h プールより少ない (top-K が効かない)。報告に窓あたりの候補数を書く
2. **乱数種** 20261104、抽出・bootstrap・Opus の抽出・腕の順序のすべて
3. **「正しい開設」「誤った開設」の定義**: 台帳に無い。Q1∧Q2∧Q3 (§5.2)。判断不能は外す
4. **合否の線**: 台帳は検定の名前だけで線が無い。P1 の下限 −0.5/窓、P2 の +5 点、P5 の 1.5 倍は本書で固定した値
   (非劣性は「改善の証明」より保守側ではなく緩い側だが、改善の証明を要求すると同等の腕を必ず落とす。誤りの側 P2・P3・P5 は厳しめに置いた)。
   P3 の ≤ 0.10 だけが台帳の `metrics` の値
5. **裁定の単位と予算**: 台帳は Opus 300。260 + 2 回目 40 に割り当てた。U が小さいときは余りを 2 回目に回さない (2 回目は最大 40)
6. **判定集の同一性**: 台帳の `gold:detect_fresh_1027` は S26-ML-GOLD が作る 60 件とされ n=null。DETECT-JUDGE が使う裁定 (本書の単位ごとの裁定) は
   別の生成物なので同じ id の「主」として登録し、60 件は副にした。**台帳の更新が要る** (`gold_sets` の n と files、`DETECT-JUDGE` の判定集の記述)
7. **日付**: 台帳の GPU-B は `2026-11-09`、依頼では 11-04 12:00。窓の範囲の終わりを `2026-11-04T00:00Z` に固定した (実行が遅れても延ばさない)。台帳の日付の更新が要る
8. **フォールバックした run の扱い**: 出荷腕の値に入れず P4 で数える (§5.1)
9. **形とモデルの分離**: 現行腕の shadow 記録を参考に出す (判定に使わない)
