## 1. 判定 (変えない)

`judged = flat OR (pir AND ((geo_cue AND (QW OR QC)) OR (cyber_geo_cue AND QD)))`

- 語の関門・問い QW / QC / QD の文言・しきい値 0.5 (固定。調整しない)・式は上の commit の中身のとおり
- 救済と問いのモデル = `step:triage_geo_rescue` の割当 (`kuebiko-sft:26b`)。`Step.GEO_RESCUE_JUDGE` が継承する。
  行ごとに pir のモデル (`model`・`model_digest`) と問いのモデル (`judge_model`・`judge_model_digest`) を記録する
- 本番の救済の prompt が既に pir (`prompt_mode = pir`) の行は、本番の判定をそのまま pir の判定として使う
- 問いを当てるのは、本番の v2 が問う候補 (flat が救わず、pir が救い、手掛かりのある記事) だけ
- 判定の入力 = 題 + `ArticleTriage._triage_content` (本文プレビュー、冒頭 1,500 字)。**記録はその入力そのもの**
  (`title`・`input_text`) と種類・sha256 を持つ。置き場はローカルの DB だけ。公開面の書き出しはこの表を読まず、
  集計 API は件数だけを返し、ログには出さない

## 2. 窓

- **START** = `geo_rescue_shadow` の最初の行の `created_at` + 24 時間 (記録から決める)
- **END** (2026-11-05 変更、§6): 「`START + 14 日` の**直前**の 00:00 UTC」(= `START + 14 日` を含む UTC の暦日の 00:00) 以降の
  00:00 UTC のうち、標本の枠 (§3) が judged yes ≥ 120 行・judged no ≥ 400 行になった最初の 00:00 UTC。
  `START + 30 日` の 00:00 で打ち切り、そのときの件数で抜く
- 救済のモデルの digest (記録の列 `model_digest` と `judge_model_digest`、判定した行の値) が窓の中で変わったら、
  窓は変わる前の最後の行の `created_at` で終わる。件数は記録の列から数える
- **枠を固める時刻** = END + 24 時間 (2026-11-05 変更、§6。変更前は 72 時間)。標本はその後に抜く。
  `pending` の `expired` への切り替え (作成から 72 時間) は変えない。固める時刻に `pending` の行は §3・§5 のとおり
  「判定されなかった行」として数える
- 見込み: 候補は約 50〜65 件/日 (10-12〜10-29 の落選の記録)。14 日で約 700〜900 行。v2 の judged yes の率は未知
  (v1 の判定は候補の 28%、v2 は絞りが強く 10〜20% の見込み) で、judged yes は 14 日で約 70〜200 行。足りなければ END は延びる

## 3. 標本の枠と抽出

- **候補** = 窓の中 (`START <= created_at < END`) の `geo_rescue_shadow` の行。同じ article_id が複数行ある場合は
  最初の行だけを使う
- **枠** = 候補のうち `status = 'ok'` (v2 の判定がある) で、モデルの digest が欠けていない行。標本は枠からだけ抜く
- **判定されなかった行**: `expired`・枠を固める時刻にまだ `pending` の行・`error` の行・digest の欠けた行。
  種類別の件数を、flat が救った行と救わなかった行に分けて報告する (層 = judged は判定されなかった行には無いため)
- **層と件数**: 層 Y = judged yes から `min(150, |Y|)` 行、層 N = judged no から 300 行を抜く
  - 抜き方: 層の中で article_id の昇順に並べ、`random.Random(20261111)` で混ぜ、先頭から取る
  - 重み = 層の行数 ÷ 抜いた行数 (逆確率重み)
- **入力の欠けた行**: `input_text` が空の行、または `sha256(title + "\n\n" + input_text)` が `input_sha256` と違う行は、
  正解を付ける前に外す (起きないはずの経路の欠け。件数を層別に報告し、重みは層の中で使える行だけで計算し直す)
- 件数の根拠 (v1 の探索の値を当てはめた見込み):
  - v1 では judged yes のうち正解 yes が 31%、judged no のうち 3.2% だった
  - v2 で judged yes の精度が 25% まで下がっても、正解 yes ≈ 150 × 0.25 + 300 × 0.035 ≈ 48 で、yes ≥ 30 になる確率は高い

## 4. 正解 (盲検)

- 付け手は新しい文脈の Opus。v1 の分析・この文書の §1〜§3・モデルの出力・ソースの名前と url・層は見せない
- **定義は v1 の追補の A〜D・A′・C′ のまま** (`docs/replay_prereg/geo_rescue_judged.md` の追補の文を変えずに渡す)。
  行ごとに rescue (yes/no)・confident・理由 1 文を付ける
- **入力** = 判定が見たものそのもの: 記録の `title` と `input_text` を盲検の入力にする (取り直さない)。
  付け手には伏せ字の連番・題・入力だけを渡す
- **κ**: 正解の yes から最大 30 行と no から残りを合わせた 60 行を `Random(20261112)` で選び、別の新しい文脈の Opus が
  付け直す。一致率と Cohen の κ を報告する。κ < 0.6 なら「正解の不安定」と明記する (線には使わない)

## 5. 合否の線 (v1 と同じ線。重み付きの推定と区間)

区間は層別の bootstrap (10,000 回、`Random(20261113)`)。次の 4 本をすべて満たせば合格:

1. 回収: judged の重み付き回収 ≥ 0.70 かつ ≥ pir の重み付き回収 − 20 pt
2. 主検定 (v1 の McNemar の代わり。重み付きの標本では McNemar をそのまま使えないため): judged の重み付き回収 −
   flat の重み付き回収 の差の、層別 bootstrap の 95% 区間の下限 > 0
3. 誤救済: judged の重み付き誤救済率 (正解 no のうち judged yes の割合) ≤ 20%
4. 総量: 枠の中の judged yes の割合 ≤ 50% (表から直接。正解は要らない)

**記録の経路の確認** (合否の線ではない): flat が救った行のうち judged が救う割合。式の上で judged ⊇ flat なので 100% に
なるはずで、100% でなければ記録の経路の不具合として報告し、原因を直すまで判定を保留する

**無効** (判定しない):
- 候補のうち、判定されなかった行 (`expired` + 枠を固める時刻の `pending`) が 10% を超える
- 判定の失敗の率が 5% を超える。率 = `status = 'error'` の行 ÷ (`status = 'ok'` の行 + `status = 'error'` の行)
  (判定の段が手を付けた行が分母。`pending`・`expired` は含めない)
- 抜いた標本の正解 yes < 30
- 窓の中で救済のモデルの digest が変わり、§2 の打ち切りの後の件数が §2 の基準に届かない
- この文書のコミットの後に、§1 の判定 (語の関門・問い・しきい値・式) を変えた

**報告のみ**: 層別の値、confident だけの値、κ で一致した行だけの値、手掛かりの種類別の件数、外した行の内訳、
入力の種類 (本文 / 概要) 別の値、本番での追加の負荷 (判定の段の 1 時間あたりの所要と件数。`job_run_log` の
`geo-rescue-shadow-hourly` の段の所要と、ログ `geo_rescue_shadow_judged` の件数から)

    3. 72 時間待てば拾えた「遅れて判定された行」(判定の段が止まった・障害後に追いついた行) を拾えない。段が長く止まった場合は
       無効の条件 (判定されなかった行 > 10%) で検知する
    4. 判定されなかった行の数は、固める時刻の SELECT で数え直して報告に必ず書く (種類別: `expired`・`pending`・`error`)
