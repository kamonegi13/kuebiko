# 事象中心のナレッジグラフ / GraphRAG — 何ができ、何を改善し、何を表せるか (2026-09-26)

利用者との検討の整理と、検証の計画・結果。**結論を先に書かない** — 各仮説は既存の正解セットで
測ってから採否を決める (§5)。

## 1. なぜ「事象中心」か

| 観点 | アクター中心 | 事象中心 |
|---|---|---|
| 載る範囲 | 帰属できた事象だけ | すべての出来事 (帰属不明のランサム主張・脆弱性の公表・原因不明の被害を含む) |
| 精度の源泉 | 主題判定を通った記事 | 事象 = 複数記事の束。独立媒体数という裏付けを持つ |
| 時間 | 月次の射影 | 初報・続報・最新の時刻を元から持つ |
| 既存資産 | actor_observed_profile (187 アクター × 月) | 事象ニュース・台帳・種別・深刻度の軸・entity |

アクター中心の射影 (actor_observed_profile) は事象中心グラフの **1 つの見方** として残る。

## 2. グラフの構成 (既存の層を線として繋ぐ)

- 節点: 記事 / 事象 (event_items) / 台帳 (situations) / entity (CVE・アクター・マルウェア・
  被害組織・製品・ベンダ・国・業種)
- 線 (すべて **出典の記事・時刻・信頼度** を持つ):
  - 記事 → 事象 (群化、既存)
  - 事象 → entity (役割つき: 主題 / 言及。事象内の記事数と独立媒体数を重みに)
  - 事象 ↔ 事象 (同じキャンペーン / 続報 / 同じ CVE の別件。**因果の線は引かない**)
  - 事象 ↔ 台帳 (証拠として属する。残タスク B4)
- 保存は PostgreSQL の表 (専用グラフ DB は不要 — ベクトルと同じく規模が小さい)

## 3. 何ができるか

### 3.1 精度を上げる (パイプラインの各段)
| 段 | 既知の弱点 | グラフで変わること | 物差し (既存) |
|---|---|---|---|
| 台帳への証拠の割当 | 規則由来の精度 anchor 31% / nation 10% / token 4% (09-24) | 記事単位 → 事象単位の顔ぶれで判定 | assign_goldset 662 |
| detect (新規追跡の選定) | 記事単位で「新しさ」を測れない | 「初めて引かれた線」を特徴量に | detect goldset / replay |
| 事象の群化 | 埋込が書式を測る。群単位 83% | 珍しい entity の共有・2 段先のつながり | ペアのラベル |
| triage | 記事単独の判定 | 追跡中の台帳・活動中のキャンペーンとの接続 | triage goldset |
| 状況総括・ACH | 過去文脈をキーワードと期間で集める | 台帳 → 事象 → 記事の構造で根拠を集める (GraphRAG) | 対読審判 |

### 3.2 誤りを見つける (整合性の点検 — グラフの最大の価値)
今の判定は 1 件・1 組・1 事象を単独で決める。グラフでは **判定どうしの矛盾** として誤りを検出できる。

| 誤り | 矛盾の形 | 物差し |
|---|---|---|
| 誤群化 | 推移律の破れ (A~B, B~C, A≁C)・事象内の顔ぶれの分裂・珍しい entity を共有する別事象 | ペアのラベル |
| 誤分類 | 事象内での種別の食い違い・同じ名前が actor / malware / tool に割れる | Opus の種別ラベル・辞書 |
| 誤関係 | 証拠と台帳の中心の顔ぶれが重ならない (= B1 弱い証拠)・事象に相容れない帰属・行動史に合わない標的 | assign_goldset |
| 別名 | 別 id の 2 名が同じ事象・被害組織・マルウェアと強く共起 | 辞書の既知の別名 |

**限界**: 見つかるのは周りと食い違う誤りだけ。一貫した系統誤り (辞書自体の誤り等) は正解セットの評価で捉える。

### 3.3 表す (分析官に意味のある情報)
- **新しい線 = 構造変化**: アクターが初めてその業種・国を狙った / CVE が初めてランサムに使われた /
  同じ組織の 2 度目の被害 → 早期警戒 (I&W) の経路へ
- **キャンペーンの時系列**: ばらばらの報道を 1 本の流れとしてたどる
- **多段の問い**: 分析チャットで「直近 3 か月に日本の製造業を狙った事象で悪用された CVE と関係アクター」
- **似た過去の事象**: 同じ CVE・アクター・業種・種別で探す (本文の埋込が書式に引かれる問題を避ける)

### 3.4 GraphRAG
Microsoft GraphRAG は LLM で entity と関係を抽出し、塊 (コミュニティ) ごとに要約を作る。kuebiko では
**塊 (台帳・キャンペーン・事象) が既にある** ので LLM による関係抽出は不要。台帳・キャンペーン・
アクター・CVE の単位で要約を持ち、ACH・状況総括・分析チャットはそれを構造でたどって参照する。

## 4. 原則と危険

1. **自己強化を防ぐ**: モデルの出力から作ったグラフをモデルの入力に戻すと誤りが増幅する (台帳の汚染と同じ構造)。
   判定・検索に使う線は **高精度の層だけ** から作る (主題判定・2 媒体以上の裏付け・CVE)。
2. **線の多さを重要性の代わりにしない** (CLAUDE.md「収集量を重要性の代理にしない」)。
3. **検出器は精度を測ってから使う**: 高精度 (目安 90% 以上) は自動訂正、他は確認待ちの一覧
   (確認はまず Opus、その要約を人が評価)。訂正は元の判定を上書きせず別記録 (戻せる)。
4. **関係抽出は難しい**: 実務条件の ATT&CK 抽出でも micro-F1 0.22 (arXiv 2606.18166)。LLM に関係を推測させず、
   既存の構造 (群化・主題判定・台帳) を線にする。同じ記事に出ることは関係ではない (言及 ≠ 主題)。

## 6. 結果 (2026-09-26、DB の読み取りのみ・LLM 呼出なし)

主要な数値はスクリプトを再実行して再現を確認した。**n が小さいものは参考値**。

### 6.1 精度を上げる (H1-H3、assign_goldset 662)
| # | 結果 | 判定 |
|---|---|---|
| H1 | AUC: 記事単位 0.759 / 事象単位 0.764 / 要約の埋込 0.876。複数記事の事象 (n=201) に限ると 0.832 / 0.875 / 0.867 | **不採用**。事象単位が効くのは複数記事の事象だけで、それでも埋込と同等。gold の 7 割は 1 記事の事象 |

### 6.2 誤りを見つける
正解ラベルの制約: 群化の人手ラベル 365 組と本番の判定記録 (event_pair_shadow 7,083 組) の重なりは 2 組だけ。
D1/D4 の精度は 26B の独立判定 (365 組で正答 85.8%) を参照にした推定値。

| # | 検出器 | 結果 | 判定 |
|---|---|---|---|
| D1 | 推移律の破れ | 67 群 (3 件以上の群の 34%) に矛盾。「三角形で最も確信度の低い辺」は無作為以下 (21% vs 24%) — 少数派の「別」の辺を選んでしまう。**2 本の「同一」の辺のうち低い方**に絞ると 46% (基準率 18% の 2.6 倍) | 確認待ちの並べ順 |
| D2 | 事象内の顔ぶれの分裂 | 20 事象。誤結合の的中 8% (1/13)、人手ラベル 4 組はすべて同一 — 分裂の大半は entity 抽出の欠落・表記揺れ | **不採用** (抽出の網羅率監査には転用可) |
| D3 | 珍しい entity を共有する別事象 | 1,632 組。人手ラベルで同一 72% (47/65)。**被害組織だけの共有は 80% (36/45)**、マルウェア名だけは 38% (3/8) | **最も有望**。確認待ちの統合候補。自動統合には n も精度も不足 |
| D4 | ハブ記事 (週次まとめ等) | 「同一」の判定の誤り率がハブ絡み 25% vs それ以外 13%。推定誤りの 51% がハブ絡み | 単独でなく群化の**危険度の特徴量**として |
| C1 | 事象内の種別の食い違い | 93 事象。目視ではほぼすべて正当 (同じ CVE の勧告と悪用報道、事象についての論評に other)。Opus ラベルとの重なりは 1 件 | **不採用** |
| C2 | 同じ名前が actor / malware / tool に割れる | 233 名。actor×malware の 105 名は RaaS の自称名 = 正当な二重性。**malware×tool の 128 名** (AsyncRAT 等が tool に、Evilginx 等が malware に) は実際の揺れで、出現 5 件以上なら多数決の中央値 83% | **辞書拡充の確認待ち** (malware_aliases.yaml の tools) |
| C3 | 共起による別名候補 | 上位は別実体ばかり (同じ報告で並べて特定された 3 クラスタ、イラン APT の比較記事、共有 MaaS)。辞書から検証できる唯一の真の別名は 25,200 組中 1,700 位 | **不採用**。本文の aka 明記を使う既存設計 (F3) が妥当 |
| C4 | 新しい線 (直近 30 日初出・過去 180 日なし) | 言及ベースの CVE の新線 1,007 本のうち主題判定で裏付くのは 2.5%。主題ベースのマルウェアの新線 256 本は 91% が実際の新ツールと整合 (自己ブランド 9% を除く) | **主題ベースなら確認待ち・I&W 候補**。文言は「本コーパスで 180 日ぶり」— 再登場 (既知マルウェアの活動再開) を「新発見」と書かない |

### 6.3 結論
1. **効いたのはすべて、線を高精度の層から作った場合** (被害組織の共有・主題判定・辞書)。LLM の生のタグや
   言及・共起から作った線は、正当な多様性や別実体を誤りと取り違える (C1・C3・C4 言及版・D2)。§4 の原則 1 は実測で支持された。
2. **割当・類似の判定そのものは、要約の埋込がグラフより強い** (H1・H2)。グラフは埋込の置き換えでなく、
   埋込が見られない **判定どうしの矛盾** と **構造の変化** を見る道具として価値がある。
3. **自動訂正に使える精度の検出器は無い**。確認待ち (まず Opus、その要約を人が評価) に回す価値があるのは
   D3 (被害組織の共有)・C2 (malware/tool の揺れ)・C4 (主題ベースの新しい線)・D1 (並べ順)。
4. **未検証**: GraphRAG で ACH・状況総括・分析チャットの根拠を集める効果 (§3.4) は LLM の対読審判が要るため今回は測っていない。
   D4 を群化 ML の特徴量に足す効果は、ペアのラベルで学習・評価して測る必要がある。

### 6.4 実装するなら (順に)
| 順 | 内容 | 前提 |
|---|---|---|
| 1 | D3: 被害組織だけを共有する別事象を統合候補として一覧 → Opus で確認 → 採否を記録 | 記録がラベルになり n=45 を増やせる。精度 90% 超の条件が見つかれば自動統合を検討 |
| 2 | C4: 主題ベースの新しい線を I&W の確認待ちへ | 自己ブランドの除外・文言 |
| 3 | C2: malware/tool の揺れ (出現 5 件以上) を辞書の追記候補として一覧 | 追記は人の承認 |
| 4 | D4: ハブ度を群化 ML の特徴量として試す | ペアのラベルで検証 |

## 7. 文献から見た「足りないもの」(2026-09-26)

主要な数値は原典で確認済み (Finkel & Manning・Pujara & Getoor は本文、GraphRAG-Bench・Ranked by the Matcher は要旨)。

| 足りないもの | 文献 | 示唆 |
|---|---|---|
| **全体の整合を同時に解く推論** — 今は 1 組ずつ独立に判定し、矛盾を後から「検出」している | Finkel & Manning, ACL 2008 (推移律を ILP で強制: B³ 最大 +3.6%、群の F 最大 +16.5%) / Pujara & Getoor, arXiv:1607.00992 (PSL で推移律等を同時に解く: NELL で F1 0.333→0.453) / Bansal et al. 2004 (相関クラスタリング) | 推移律の破れは検出器でなく**制約**として群化に入れる。群単位で効く (今の 83% は群単位) |
| **問いの種類** — 今回測ったのは単発の照合 (割当・類似)。グラフが勝つのは多段・集約の問い | Xiang et al., arXiv:2506.05690 (「GraphRAG は多くの実タスクで通常の RAG に負ける」) / Han et al., arXiv:2502.11371 (単発・詳細は RAG、多段は GraphRAG) / HippoRAG, arXiv:2405.14831 (多段 QA で最大 20%) | §6 の負の結果は予想どおり。**本来効く領域 (状況総括・ACH の根拠集め、分析チャットの多段の問い) は未測定** |
| **ラベルの使い方** — 群化ペア 365 組と本番の判定記録の重なりが 2 組。検出器の出力もラベルにしていない | Kasai et al., ACL 2019 (能動学習で数百ラベルで全ラベル同等) / Snorkel, arXiv:1711.10160 (弱い規則を束ねて学習ラベルに) | 確認待ちの結果を記録してラベルに戻すループが無い |
| 線の役割 | Gao et al., arXiv:2406.15990 (事象の引数役割は有効だが役割抽出の精度で頭打ち) / CASIE (AAAI 2020) | 既存の高精度の役割 (主題判定・被害組織) を使い切るのが先。新しい役割抽出は後 |
| 測り方 | Hakim & Song, arXiv:2609.01671 (CTI の KG 抽出は照合方式だけで F1 0.16-0.70 に振れる。ローカル LLM に検証層を足すと precision が下がった) | 検出器の精度は照合・正解の定義を変えて再測定する |

LLM に共参照を丸投げしても解けない (GPT-4 単体で CoNLL F1 が GVC 7.6 / FCC 0.0、Min et al. ACL 2024)。
小さなモデル + LLM の知識、という今の構成は文献と整合する。

### 次の検証 (提案)
1. **群化を相関クラスタリングで全体最適化**: 群化 ML のペア確率を辺の重みに、被害組織の共有・ハブ度を補正に使う。
   群単位の正解率 (現 83%) で比べる。LLM・GPU 不要
2. **GraphRAG を集約の問いだけで比べる**: 状況総括・ACH の根拠を「台帳→事象→記事の構造」で集めた場合と現行を、対読審判 (位置の入れ替えつき) で比べる
3. **確認待ち → ラベル化のループ**: D3 等の候補を Opus で確認し、結果を群化のラベルに戻す (能動学習)

## 8. 検証: 群化を相関クラスタリングで全体最適化 (2026-09-26)

**方法**: 本番の判定記録 (event_pair_shadow、7,083 組・1,956 記事、特徴量を保存済み) を今の群化 ML で確率化し、
重み logit(p) − logit(閾値) の総和を最大にする群分けを、本番の群を初期値に局所探索で求めた
(記事の移動・群の統合・独立、改善量 1.0 超の手だけ採用)。観測されていない組は中立 (0)。
本番と仲間が変わった 139 記事を、**どちらの案か伏せて** Opus が裁定した (候補の順は記事 id のハッシュで入れ替え)。

| 食い違いの種類 | 件数 | 組み直しが正しい | 本番が正しい | その他 |
|---|---|---|---|---|
| 単独 → 群 (取り残された記事を入れる) | 50 | **47 (94%)** | 3 | |
| 群 → 単独 (群から外す) | 23 | 4 (17%) | **19** | |
| 群 → 別の群 | 66 | 7 | 6 | 両方と同じ 51 / どちらとも別 2 |

- **統合の方向は効く、分割の方向は効かない**。分割は ML が「同一」を低く見積もる癖 (書式が違う同じ出来事) を
  そのまま負の証拠にしてしまう。09-02 の遡及分割の較正 (厳しい閾値でしか安全でない) と同じ結論
- 「両方」51 件は、同じ出来事が 2 つの群に割れていることを示す。ただし目視では、Opus がまとめ記事と
  個別記事・別被害組織の主張の混ざった群まで「両方」としたものを含む (甘い)。この行は数に使わない
- **取り残しの原因**: 47 件すべてで、本番の ML は承認した辺を 1 本以上記録していた。それでも単独のままなのは、
  参加時の定足数ガードと統合段の `MIN_EDGES_BETWEEN_ITEMS = 2` が **辺の本数** でハブを抑えているため
  (相手が 1 件の事象なら辺は構造上 1 本しか張れない)。相関クラスタリングは本数ではなく **賛否の重みの総和** で判断する
- 誤り 3 件はすべて日次ダイジェスト・複数被害のまとめ (ハブ)。まとめ・件数の特徴 (roundup_one / count_one 等) が
  立つ組を除くと **40/41 (98%)**、代わりに正しい 7 件を落とす

### 結論
文献の予想 (整合をまとめて解くと群単位で効く) は **統合の方向についてだけ** 成り立った。
実装するなら、統合段に「辺の本数」ではなく「重みの総和」で判定する経路を足す — まとめ系の特徴が立たない組に限り、
承認辺 1 本でも反対の証拠が無ければ繋ぐ。分割には使わない。

## 9. なぜ分離の方向に使えないか (2026-09-26)

### 実データ (§8 の「群→単独」23 件と本番の群)
1. **形が観測されていない**: 3 件以上の群 389 個のうち 205 個は群内の組が 1 つも評価されていない
   (観測率 中央値 0%・平均 37%)。判定記録は「参加のときに候補 × 一部のメンバー」しか評価しない
2. **確率の低さは「別」の証拠ではない**: 外すべき記事と残すべき記事で、群との組の形 (強い辺の数・確率の並び) は同じ。
   **矛盾の証拠 (被害組織の食い違い) はどちらもほぼゼロ**で、全組が固有名を共有していた。
   違うのは「似ていない」ことだけ — 同じ出来事の別の側面 (勧告・悪用・修正・解析) は互いに似ていない
3. **外すべきだった 4 件はすべて一括勧告** (CISA KEV 追加・複数製品の脆弱性公表)。ほぼ同じ一括勧告を Opus は別の群では「残す」と裁定した。
   1 つの記事が複数の出来事に属するのに、群は 1 つにしか入れられない — **正解そのものが定まらない**

### 文献
| 論文 | 結果 | 含意 |
|---|---|---|
| Gruenheid, Dong, Srivastava, VLDB 2014 (増分の名寄せ: 統合・分割・移動) | 本文で確認: 検討した統合 115 件のうち実行 88 件、**分割は 44 件のうち実行 1 件**。「統合の方が分割よりずっと多い」 | 分割を正当化する証拠は統合よりずっと出にくい (同じ非対称) |
| Barton, Neiman, Yuan, arXiv:2105.05957 (群が壊れているかの判定) | 本文で確認: 雑音の多い条件で F1 推移閉包 0.375 / 群単位の特徴 (SuperPart) 0.619 / GNN 0.687。「10 件の群で 1 件が外れても、45 組のうち 9 組にしか現れない」 | 外れは組の多数決で薄まる。群単位で見ると効くが、それでも 0.7 前後 |
| Raad et al., ISWC 2018 (同一性リンクの誤りをコミュニティと密度で検出) | 誤り度の低い側は 100% 正しい。ただし 5.5 億本の密な網が前提 | 形で見る方法は **密な観測** があって初めて効く |
| Guéret et al., ESWC 2012 (媒介中心性等の局所指標) | 精度 49% / 再現率 68% (100 リンク、survey 経由) | 疎な局所の形だけでは弱い |
| Wagstaff et al., ICML 2001 (must-link / cannot-link) | — | 「確率が低い」と「相容れない」は別の種類の情報として扱う |

### 何を足せば分離に使えるか
| 足すもの | 理由 | 見込み |
|---|---|---|
| **群内の組を全部評価する** (ML のみなら LLM 不要) | 形が見えないと橋も切断点も分からない | 09-02 の遡及分割は全組評価 + 連結成分 (t=0.70) で群 P 100% / R 70% を出している = 密なら既に使える |
| **重みの総和ではなく連結性で割る** | 「似ていない組が多い」は多面的な出来事でも起きる。「繋がる道が無い」は起きない | 利用者の直感 (形) はこちら。§8 の失敗は重みの総和を使ったため |
| **矛盾の証拠を別の経路に** (被害組織の食い違いに加え、CVE の集合が重ならない・製品が違う) | 分割の根拠は相容れなさだけに限る (cannot-link) | 脆弱性系の群には今この経路が無い |
| **一括勧告を「関連」で持つ** (群のメンバーにしない) | 多対多の記事を 1 群に押し込むから形が歪む。割るのではなく表し方を変える | 外すべき 4 件はすべてこれ |
| 群単位の判定 (SuperPart 型) + 群単位のラベル | 外れは組の単位では薄まる | 文献でも F1 0.6-0.7。ラベル (Opus の群監査) が要る |

### 原理的に難しいもの
- **多面的な出来事** は、正しく組んでも形が「疎」に見える (勧告と解析と修正は互いに似ていない)。形だけで割ると正しい群を壊す
- **一括勧告** は 1 群への所属という前提そのものが合わない。検出器ではなく表現の問題
- **疎な観測** のままでは形が見えない — これは足せば解ける (評価の計算量の問題)

**グラフの役目は台帳に無いキャンペーンの発見・台帳の重複の発見・台帳の証拠の事象単位での整理**。

## 11. 関係は持たずに導く (2026-09-26、利用者の提案)

関係を別の表に書くのではなく、**事象 → 指標 (CVE・主題アクター・マルウェア・ツール・被害組織・製品) の線だけを持ち、
事象どうしの関係はその線の重なり方から計算する**。§10 のキャンペーンの線もこの方法で出している。

利点: 関係の表が指標とずれない (SSoT が 1 つ)・書いたきり読まれない列を作らない・定義を変えれば過去にも一様に効く・
キャンペーンは「指標でつながった事象の塊」としてそのまま現れる (GraphRAG の塊)。

**ただし線に属性が要る** — これが無いと §6 の失敗 (言及・まとめ・自己ブランドの雑音) が再発する:
| 線の属性 | なぜ | 今あるか |
|---|---|---|
| 役割 (主題 / 言及 / 被害 / 焦点の CVE / 列挙された CVE) | 言及の線は雑音 (§6 C4: 言及の CVE の新線は 97.5% 雑音) | 主題アクターと被害組織はある。CVE は件数 (3 以下) で焦点を近似 |
| 事象の種別 (勧告・悪用・被害・まとめ) | 側面・包含の判定に必須 | **直近 30 日の事象メンバーの 32% にしか付いていない** |
| 珍しさ (その指標を持つ事象の数) | 「ランサムウェア」級の汎用語は線にしない | 計算で出せる (merge の hub_cap と同じ) |
| 裏付け (事象内の記事数・独立媒体数) | 1 記事だけの言及を弱く | 事象に独立媒体数がある |

関係の種類は (共有する指標の種類 × 役割 × 両事象の種別 × 時間差) の関数として決まる:
側面 = 同じ焦点 CVE / 被害組織 + 種別が違う・包含 = まとめ・多 CVE の事象が複数の事象と CVE を共有・
続報 = 同じ被害組織 + 期間が離れる・同一キャンペーン = 同じ主題アクター + 珍しい道具 / CVE を共有 + 被害が違う。

**書くのは判定の結果だけ** (Opus・人が「この関係は正しい / 誤り」と確認したもの)。これが上書きとラベルになる。
例外は **同一** — これは指標から導けず、今の群化そのもの。

## 12. 指標どうしの関係を多層でつなぐ (2026-09-27、利用者の提案)

指標どうしの関係は同一 / 別だけでない。組織 → 業種・国、アクター → 帰属国・動機・種類 (APT / ランサム / 国家背景 / IAB)、
CVE → 製品 → ベンダ、マルウェア → ファミリー → 使用アクター。これらの関係で事象を結ぶと、群と群の関係が多数でき、
単一事象では見えない型が現れる。**異種情報ネットワークのメタパス** (Sun et al., PathSim, PVLDB 2011) と同じ考え方:
「事象 → アクター → 帰属国 → アクター → 事象」のような型の並びごとに関係を定義する。

## 13. 位置づけ — 根本的に変えるのか (2026-09-27)

**変えないもの**: 収集・抽出・群化 (同一の判定は ML + 埋込)・台帳への割当 (埋込が強い、§6)・保存先 (PostgreSQL の表)。
**変えるもの**: 関係の「読み方」。今は群化・台帳・PIR・地図がそれぞれ自前の規則で entity を読んでいる。これを
(1) 事象 → 指標 (役割つき)、(2) 指標 → 指標 (型と階層つきのオントロジー) の共通の層に揃え、関係はそこから導く。
データモデルとして本当に変わるのは 1 点だけ — 一括勧告・まとめが複数の事象に属すること (多対多)。
これも所属を変えずに「包含」の関係として導けば、群化はそのまま残せる。

**KG / GraphRAG としての意味**: 検証 (§6-§12) と文献で一致したのは、
- 似ているかの判定 (割当・類似) では、グラフは埋込に勝てない → 置き換えない
- 型のある多段の問い・集約の問い・判定どうしの整合・構造の変化は、埋込では原理的に見えない → ここがグラフの領分
  (取り残しの救済 94%・キャンペーンの線・台帳に無い追跡候補・台帳の重複・主題ベースの新しい線)
- GraphRAG が通常の RAG に勝つのは多段・集約の問いだけ (arXiv:2506.05690, 2502.11371)。多層の型付き関係は、
  その問いを立てられるようにするもの。LLM で関係を抽出する一般的な GraphRAG と違い、辞書と主題判定から作れる

**原則**: グラフは発見・説明・整合の点検に使う。判定 (群化・割当・配信) は ML と埋込のまま。
グラフ由来の結果を判定に戻すのは、盲検で精度を測ってから (自己強化の防止、§4)。

### 段階
| 段 | 内容 | 単独の価値 |
|---|---|---|
| 0 | アクターの属性 (帰属国・種類・上位組織) を埋める | 既存の国家情勢・PIR・脅威評価にも効く |
| 1 | 導出する関係を型ごとに定義し、盲検で精度を測る (側面・包含・続報・キャンペーン・共通の供給元・商品化) | 何が使えるかが分かる |
| 2 | 精度が出た型を発見の面へ (追跡候補・台帳の重複・I&W・取り残しの救済) | 分析官の目に届く |
| 3 | GraphRAG: 状況総括・ACH・分析チャットの根拠を構造でたどり、現行と対読で比べる | 集約の問いの質 |

## 14. 可視化と保存先 (2026-09-27)

実測: 事象 11,685 / 指標 16,934 / 事象 → 指標の線 47,650。全体を集計する SQL が 0.12 秒。
1 年分でも数倍で、グラフ全体がメモリに載る規模 (数十万本)。

- **保存先は PostgreSQL のままでよい**。正本を 1 つに保てる (グラフ DB を足すと二重の正本・同期・バックアップが増える)
- 導出する関係は毎時の段で表 (実体化したビュー) に書き出し、索引を張る
- 塊 (コミュニティ)・中心性・配置は Python (igraph / networkx) で毎時計算し、属性として保存。画面の要求ごとには計算しない
- API は「部分グラフ」を JSON で返す (ある事象・アクターの近傍 2 段、ある塊、ある期間)。全体を一度に描かない
- 描画の律速はブラウザ (数千ノードを超えると見づらく重い)。WebGL 系 (Sigma.js 等) か、小さな部分グラフなら Cytoscape.js
- Cypher で問い合わせたくなったら、PostgreSQL の拡張 (Apache AGE) で同じ DB に載せる選択肢がある (版の対応は導入時に確認)
- グラフ DB が要るのは、数千万本の線を対話的な速さで任意の深さまでたどる場合。この規模・単独運用では当たらない

## 15. 事象どうしの関係は埋込で見えるか (2026-09-27)

利用者の整理: 記事どうしが似ているかは埋込、群になった事象どうしの関係 (似ているか・キャンペーンか・どんな関係か) は
埋込では厳しい → グラフが補完する。これを直近 60 日の事象で測った (事象の埋込 = メンバー記事の埋込の平均)。

| 事象の組 | 組数 | cos 中央値 |
|---|---|---|
| キャンペーン (同じ主題アクター + 珍しい道具・CVE を共有 (10 事象以下)・被害組織は別) | 67 | 0.572 |
| 同じ主題アクター・道具・CVE・被害の共有なし | 91,677 | 0.564 |
| 別々のランサムグループ・共有なし | 352,337 | 0.386 |
| 無作為 | 20,000 | 0.380 |

- キャンペーン vs 無関係・無作為: AUC 0.87-0.88 — **関係があるかどうか (話題が近いか) は埋込で見える**
- キャンペーン vs 同じアクターの別の活動: **AUC 0.515 = 偶然と同じ**。埋込は「同じアクターの話」までは分かるが、

- 埋込 = 関係がありそうな事象の候補を広く拾う (再現率)

## 16. キャンペーンの定義を多次元に (2026-09-27、利用者の指摘)

§10・§15 の「同じ主題アクター + 珍しい道具・CVE + 被害は別」は測りやすさを優先した**狭い代理**だった。
キャンペーンは時期・標的の業種・手法・帰属国などでも結び付く。
- MITRE ATT&CK の Campaign: 特定の期間に共通の標的と目的で行われた侵入活動の集まり。**帰属していなくてもよい**
- Diamond Model (Caltagirone et al. 2013、`src/cti/diamond_model.py` が採用済み) の活動群: 攻撃者・能力・インフラ・被害の
  4 頂点と、時刻・手法などの付帯特徴の近さで事象をまとめる
→ 主題アクターは **必須条件ではなく次元の 1 つ**

### 次元ごとの材料 (直近 60 日の事象 11,283、事象内のどれかの記事に値があれば有り)
| 次元 | 材料 | 網羅 |
|---|---|---|
| 時期 | 事象時刻 | 100% |
| 攻撃者 | 主題アクター (帰属国・種類は辞書経由、§12) | 17% |
| 能力 | マルウェア・道具・CVE | 20% |
| 手法 | TTP (LLM 抽出、精度は未測定。実務条件の ATT&CK 抽出は micro-F1 0.22 という報告) | 43% |
| インフラ | IOC (ドメイン・IP・URL) | 5% |
| 被害 | 業種 47% / 国 45% |
| 意図 | socio_political_intent | 45% |

### 含意
- 帰属していない事象 (8 割強) も、被害・手法・時期でキャンペーンに加われる。ただし業種・国・意図は単独では粗い (§12)。
  意味が出るのは **複数の次元が同時に一致し、かつ珍しい** とき (例: 同じ業種 × 同じ国 × 同じ珍しい TTP × 2 週間以内)
- 次元ごとに強さが違う: インフラ・珍しい能力は 1 つで強い / 業種・国・意図は組合せでのみ効く / 時期は窓として効く
- 事象ごとに次元の特徴量を作り、次元別の重み (珍しさ込み) で近さを出す = Diamond の活動群の考え方。
  重みは Opus が盲検で「同じキャンペーンか」を判定した組で学ぶ (§8 と同じ手順)
- 候補は埋込で広く拾い (§15: 関係の有無は AUC 0.88)、次元の一致で種類と根拠を決める
- **TTP の精度が未測定**。手法の次元に頼る前に、CTIBench の ATT&CK 抽出 (s20 評価で予定) と、kuebiko 自身の TTP の抜き取り検査が要る

### 17.4 標準との対応 (一次資料で確認)

## 18. キャンペーンと台帳の定義 (設計、2026-09-27)

### 現状 (§17.3)
キャンペーンが 4 系統に分散: 台帳 (situations、kind = event 262 / standing 9) と situation_relations の same_campaign (2 件)・
campaign 指標 (「Operation ○○」の正規表現、302 件)・辞書の notable_campaigns (6 件)・本文書の指標から導く定義。

### 定義 (STIX 2.1 / ATT&CK に合わせる)
| kuebiko | 標準 | 定義 |
|---|---|---|
| 辞書のアクター (kind=group) | STIX Intrusion Set / ATT&CK Group | 単一の組織が主導する持続的な活動のまとまり |
| 辞書の機関 (kind=organization / contractor) | STIX Identity | 部隊の上位組織 (sponsor_org で結ぶ) |
| 台帳のうち「アクターを追うもの」 | Intrusion Set の追跡 | 主題アクターが軸。期間の終わりが無い |
| 台帳のうち「出来事の流れを追うもの」 | STIX Campaign / ATT&CK Campaign | 期間と標的で区切られた活動。**帰属は任意** (主題アクター無しで開ける) |
| 台帳 kind=standing | (常設の情報要求) | 変更なし |
| campaign 指標 | Campaign の **名前** (敵の作戦名) | 法執行の摘発作戦・軍事作戦は Campaign ではない |
| 事象どうしの「同一キャンペーン」 | Campaign への所属の候補 | §16 の多次元の近さ (Diamond の活動群の手順) で導く。台帳への所属の候補として使う |

### 実装の順 (s20 の後、台帳の割当を触るときに一緒に)
1. 台帳に型の区別を足す (event を actor 追跡 / campaign 追跡に分ける)。detect の開設で、主題アクターが無くても
   campaign 追跡を開けるようにする
2. campaign 指標の値に種類 (敵の作戦 / 法執行 / 軍事) を持たせる。既知の法執行作戦 (Endgame 等) の一覧から始める
3. notable_campaigns は辞書の自由記述のまま残し、グラフでは使わない (6 件で網羅が無い)
4. situation_relations の same_campaign / shared_nation は、§16 の導出に置き換えられるか比べてから整理する
