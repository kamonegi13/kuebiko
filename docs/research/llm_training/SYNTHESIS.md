# 統合考察: この用途に特化した LLM を post-training で作る

最終更新: 2026-09-05 夜。実測 (v1/v2/v3) と調査ノート 11 本の統合。

## 0. 目標の定義

**このツールの各用途に特化した LLM を SFT / RL で作り、ローカルで運用する。**
gemma4-26B や Ollama は手段であって前提ではない。変えない前提は
中国系モデル不可 (§4) / ローカル完結 / 日本語の生成品質 / 決定論的関門との併用。

## 1. 実測の到達点 (2026-09-04〜05)

| 版 | 構成 | 結果 |
|---|---|---|
| v1 | 事象ニュース単独 746 対 | 事象ニュースで base に有意勝利 (caveats 13勝1敗)。**未学習スキーマで縮退** (`"null"` 72% / 重複 56.8%)。triage は独立参照で区別不能。**spotlight へ正の転移・31B の 4 倍速** |

## 2. 文献との照合 — 実測は既知パターンの再現だった

- **課題型で勝敗が決まる**: 固定タクソノミーの抽出・分類は特化 SFT が GPT-4 級に勝ちうる
  (LoRA Land 25/31)。自由 narrative は汎用大規模が強い。**手元の苦戦配置はこの通り**
- **契約は速く (150 反復)、能力は遅い (700 反復で教師の 39%)**: LIMA 系の非対称性と一致
- **v2 の劣化は忘却でなく干渉**。均等混合は失敗しやすい (T5)。2 段階化するなら
  **繊細な生成を後段に** (Chained Tuning) + replay
- **CPT は見送り**: 実績下限 (数億トークン) に対し手持ち 28k 記事は一桁下
- **RLVR が噛み合う**: repo の関門 (識別子・引用・スキーマ) は reward hacking に強い
  rule-based 報酬そのもの。SFT→RL 順序に +15% の実証。⚠ MLX 実装は未成熟 → 小規模 PoC から
- **評価**: 現行を基準にしない (循環バイアス) / 39/86/150 件では稀少クラスの見逃しを統計で
  検出できない → 決定論的関門を併用 / 床を毎回取る
- **配信**: 複数 LoRA の常駐 hot-swap はどの基盤も未成熟 (llama.cpp は KV 汚染バグ #26207)。
  **fuse 済み全量モデル構成が最も堅い**
- **Format Tax**: 構造化出力の劣化はデコード制約 (-1.6pt) よりプロンプト側 (-3.9pt) が主因で、
  **訓練で緩和できる** — スキーマ下で学習する現方針を支持

## 3. 収束しつつあるアーキテクチャ

**出力様式の族で 2 つのローカル特化に分ける** (利用者提案・干渉調査の第一推奨と一致):

```
モデル N (narrative 族): 事象ニュース → spotlight → 総括へ拡張
  要求 = JP 生成品質 + 30-40 秒/件 (毎時バッチ)。軽量高速の MoE 級が適合
  初版は v1 が既に存在。31B (4 倍遅い) の退役が成立条件つきで視野
モデル S (構造化族): triage + 抽出 + 要約
  要求 = 速度×呼出数 (triage ~2,000/日)。小型 dense (Swallow 8B) が将来候補
```

- narrative の外部 (Opus/Sonnet) は**数字が出るまで段階的に維持** (完全ローカル化は
  品質差を測ってから)
- 鮮度は学習に持たせない (actor 辞書 / MITRE sync / rubric-in-DB が担う)
- 契約違反は RLVR の小規模 PoC で潰す (SFT 完了後)

## 4. 基盤は 26B に固定しない — 実測 A/B で選ぶ

パイプライン自動化により**基盤 1 候補の検証 ≈ SFT 2-4h + 評価 1.5h**。教師対 2,273 と
凍結評価 3 セットはモデル非依存。詳細は narrative_base_candidates.md:

1. **GPT-OSS-Swallow 20B** (MoE A3.6B・JP 特化・Apache 2.0) — 正面のライバル。
   検証点 = harmony 形式×schema 強制 / mlx-lm LoRA / fuse→GGUF
2. **CALM3-22B** (dense) — 反復の速さを取りに行く選択。速度実測 (1h) で足切り
3. Swallow 8B — 構造化族の第一候補 (narrative には容量リスク)
4. 31B dense — 速度で失格。夜間の教師・審判役として残す

## 5. 判定待ちの分岐 (2026-09-05 夜間 自動実行中)

```
v3 の 3 評価 → 31B の事象ニュース 39 件 → spotlight 3 PIR (v1 vs 31B)

```

## 6. 確定事項 (再検討しない、理由つき)

- CPT 見送り (コーパス一桁不足) / 教師は混ぜない (平均を学ぶ) /
  移行判断は同一物差しの実測でのみ / rationale は学習時のみの補助信号として利用可
  (推論時スキーマは不変) / どの構成でも Step 単位のモデル割当 (Tier の「割当の単位」化) が
  共通工事


## 7. 全 LLM 呼出の事後方針 (2026-09-05 確定・残り 3 群を含む)

判定基準は 5 つ: **族 (出力様式) / 呼出量 (特化が割に合うか) / リスクと人手の関与 /
測定可能性 (評価セットを作れるか) / プロンプト-重み緊張** (運用で動く基準は重みに焼かない
— 2026-08-16 の設計原則)。

| 呼出 | 事後方針 | 根拠 |
|---|---|---|
| article_summary / triage | **S 第 1 陣 (学習中)** | 教師・評価とも整備済み |
| pir_llm_judge / event_kind / pair_judge / dedup_judge | **S 第 2 陣** — S 初版の実証後に教師生成 (半日級) | 同じ「短い構造化判定」型。既存ラベルが部分的にある |
| judgment_classifier / ioc_verifier | S 第 2-3 陣 | judgment は評価ハーネス既存 |
| **synthesis_detect** | **S 第 3 陣** — 台帳供給の Recall 感度が高く、専用評価セットを先に作ってから | 大量入力の判定 = S 型だが、見逃しの代償が大きい。呼出は日数回で急がない |
| **deep_dive 選抜** | ステップ分割後に S 第 3 陣 | 現行 Step が 2 族同居 (§区分の欠陥) |
| deep_dive 生成 / spotlight / synthesis_narrative / ledger_review | **N の拡張課題** — 転移で足りるかを先に測り、不足時のみ教師生成 | v1 の spotlight 正転移が根拠 |
| **article_translate** | **当面 base 26B 維持。S に触らせない** | 2026-07-25 に haiku vs 26B の品質比較で現行を確定済 (測定済みの意思決定を尊重)。忠実変換族で S の簡潔化バイアスは切り詰めリスク。**測定された品質問題が出るまで投資しない**。将来は entity 保存・長さ比の決定論検査 → RLVR 適用余地のメモのみ残す |
| **actor_sync** | **最低優先・base 維持** | 週次・低量・**人手承認キューが安全網として既に存在**。翻訳側の解が出たら継承 |
| **assistant_chat** | **特化しない (外部 haiku / base 維持)** | 自由対話は特化 SFT が最も弱い型。対話は human-in-the-loop で誤りが可視・低リスク。**UI と共に変わる課題で、重みに焼くとプロンプト調整が死ぬ** (設計原則の「運用で動く基準」側) |
| pir_compile / selector_proposal | 特化しない | 低頻度 + 人手レビュー前提。同上の緊張 |
| precise_search (planner/reranker) | 保留 — 構造化判定なので S 候補ではあるが、量・コスト圧が無い | 圧が出たときに第 3 陣へ |

原則: **「特化しない」も測定に基づく決定にする** — translate は比較済み、dialog 系は
課題型 + 人手関与 + プロンプト可変性の 3 点で除外。逆に S へ入れるものは全て
「教師対 → 凍結評価 → 再学習 → 前後比較」の同一関門を通す。


## 8. 夜間測定の結果 (2026-09-06 02:30 確定) — 2 族分割の実証

### N (v1 = kuebiko-sft:26b) vs 31B — 両関門通過

- **事象ニュース 39 件 (対応符号検定)**: caveats 1.54 vs 1.03 (19勝2敗 p<0.001)、
  discrepancies 0.97 vs 0.62 (15勝3敗 p=0.008)、他 3 指標は同等。機械検査は両者
  クリーン (重複 0 / placeholder 0)、引用メタデータの壊れ率も同等。31B 実測 143 秒/件。
- **spotlight 2 PIR 精読 + 全固有名詞の DB 突合**: 品質同等 + v1 は単一 SNS 源の主張に
  「未確認情報・確度は低い」と自発的な但し書き (31B は無条件提示)。速度 3.8-3.9 倍。
- **v1 の既知の瑕疵 = 固有名詞の低頻度破損**: "Nanjing Xinjiuwei" → "Xinjirazu"、
  ".hl.cn" → ".hl.conn" (2 回中 1 回)。**spotlight には識別子関門が無い** —
  narrative 全面移行の条件として関門延長が必要 (RLVR の報酬候補でもある)。

### S (s1、事象ニュース抜き 1,479 対・700 iters) — 混合モデルと同水準

| | 現行 26B | v2 (混合) | v3 (2:1:1) | **s1 (S 単独)** |
|---|---|---|---|---|
| triage Sonnet 一致 (150 件) | 55.3% | 70.7% | 67.3% | **68.0%** (vs v2 McNemar p=0.219 = 差なし) |
| 寛容バイアス | +0.413 | — | — | **+0.160** |
| IOC 平均 (86 件) | 2.70 | 4.45 | 4.48 | **4.42** |
| mitre 重複 / placeholder | — | 0 / 1 | 0 / 4 | **0 / 2** |

**結論: 分割仮説は成立**。S は narrative データ無しで構造化 2 課題の水準を維持し、
N は narrative 特化のまま希釈されない。v2/v3 の干渉問題は分割で回避された。

- s1 の判定で注目: 実悪用中 0day (SonicWall SMA1000 / PaperCut) を Sonnet の medium に
  対し high と判定 — 「不一致」計上だが Recall 重視の任務ドクトリンには整合。
- 3 アーム共通の残課題: トクリュウ遠隔解析 (high→low、Sonnet=medium) と三方面ジレンマ
  (3 者不一致)。→low 方針は利用者判断待ち。

### 次の実装 (利用者承認後)

1. narrative ティア → kuebiko-sft:26b (31B 退役)。条件: 識別子関門の spotlight 延長
2. step 単位割当の実装 → triage / article_summary のみ kuebiko-sft:s1 へ
3. S 第 2 陣 (pir_llm_judge / event_kind / pair_judge / dedup_judge) の教師生成

## 11. N2/S2 (IPO/DPO) の着手記録 (2026-09-06)

### 実現可能性の関門: IPO × MoE 26B = **可** (疎通 PoC 済)

- mlx-lm-lora 3.1.2 (`--no-deps` 導入 — venv の gemma4_text.py stop_gradient パッチを保全)。
  `--train-mode dpo --dpo-cpo-loss-type ipo` が存在し、データ形式は
  `{"prompt","chosen","rejected"}` jsonl (chat template 自動適用)。
- smoke (6 対・triage 実プロンプト): **loss 0.693→0.06 / accuracy 1.0 / margin 2.8、
  adapters 保存成功**。MoE router VJP 問題なし・NaN なし。peak 44.6〜49.3GB。
- ⚠ **OOM は非決定的に発生し、正体は Ollama との GPU 共有圧** (iters 3/7=成功、6/8=失敗、
  失敗時は Ollama が 22GB 保持中)。epoch 境界説は 6/7 の反例で棄却。
  → 運用則: **本学習は Ollama 静穏時 (夜間) に単独で回す** (SFT と同じ)。
  長系列対では peak が上がるため、対の token 長に上限を敷く (組み立て時に実測して決める)。

### 材料 (蛇口だけでは足りない)

- 蛇口 (event_draft_rejects) = 3 日で 26 件 → 主材料にならない。補助扱い。
- 主材料 = **学生の実出力を rejected 側に使う乖離ペア** (on-policy に近い):
  `scripts/build_dpo_student_outputs.py` が教師プロンプトに対する S1/N1 出力を生成
  (本番同一条件: schema 制約・think=False・temp 0.2)。S1-triage 1013 / S1-summary 802 /
  N1-event 721 の 3 系列。ペア化 (乖離の判定基準) は学生出力が出揃ってから実データで決める。

### 主腕/fallback の学習カバレッジ規律 (利用者指摘 2026-09-06)

主腕は「学習+測定済み step だけ」(S1=2 step のみ、他は base 継続)。
ティア単位 fallback の穴 = **ledger_deep_review は N1 未学習の構造化出力** (縮退様式に
該当しうる) → **probe で測定済み・縮退なし** (実 Situation 3 件 × N1/31B):
- N1 は全欄充足・重複 0・placeholder 0・証拠 article_id 実形式 100%・仮説 verdict 分布が
  31B と完全一致 (leading 1 / viable 0-1 / refuted 5-6)。抜粋もむしろ長い。9 倍速。
- 観察項目: N1 の llm_confidence が 3 件とも moderate に平坦化 (31B は low/high/high)。
  n=3 で断定不可 + 本番は ACH 整合 seam が verdict を導出するため実害は限定。
  N2 の学習に ACH 課題を足すか判断する際の材料。
→ **fallback 席の学習カバレッジ問題はクローズ** (全 narrative step が測定済みになった)。


## 12. 系譜の再編成 — 拡張 SFT を IPO の前に置く (2026-09-06 利用者決定)

利用者の問い「未学習 step の教師データ SFT で精度向上があるのでは」→ ある。順序は
**「N1.5/S1.5 (task 拡張 SFT) → その上に N2/S2 (IPO)」の 1 本系譜**に再編成
(preference は SFT の上に載せるのが標準順)。走行中の学生出力生成 + 近日の IPO は
レシピ確定用 (学習率・ペア閾値・token 上限) として活かす。

### 教師データ収穫 (稼働中、Opus・リミット自動リトライ付き)

| task | 方式 | 量の目安 | train/eval 分離 |
|---|---|---|---|
| spotlight | 本番 generate_spotlight を過去日付駆動 + RecordingClient 捕獲 | ~150-200 対 (20 PIR × stride 3 日) | 直近 3 日を評価予約 |
| synthesis | 同方式 (足場 detect/ACH はローカル = 外部消費を narrative 段に限定) | ~19 窓 | 同上 |
| pair_judge | event_pair_shadow のラベル期 (09-01) 以降のみ | 700 | 時間分離 |
| event_kind | 60 日窓の記事 − ラベル 455 id | 600 | ラベル id 除外 |
| pir_judge | 本番選抜 (_load_posted_rows + state 空) ラウンドロビン | 800 | 直近 3 日予約 |

- **dedup_judge は第 3 陣へ**: 本番の候補対がどこにも記録されず忠実サンプリング不能。
  先に候補の shadow 記録を敷く (pair_shadow と同型)。

## 14. ⚠ IPO/DPO は長系列で成立しない (2026-09-06/07 実測)

## 28. ORPO 経路の根治 + N2 probe 投入 (2026-09-08 午後)

### 「loss 9.3 異常」の全容解明 — 故障ではなく mask 不在

  理由文の可読化 (決定+特徴寄与を入力、決定を覆せない — ACH reconcile と同型)

### 毎時化 (利用者提案)

ML なら ms 級 → **毎時 run に組み込み、追跡開始を最大 ~8h 前倒し** (I&W 整合)。
ガード: ①採点済み記憶で羽ばたき防止 (毎時は新着+中間帯のみ、07-30 リサイクル教訓)
②開設時の全接地 ACH は事象駆動のまま (open ~2/日でコスト中立)。

### 手順: ラベル設計→分布監査→GBT→shadow 併走 (ペア ML パターン)→cutover。
実装着手は明日。今夜のリプレイは LLM ベースライン + s16 交換可否の測定として活用。

### §33 追記: リプレイの中身精査 — detect は「選抜くじ引き」と確定 (2026-09-10 朝)

数字 (対照 10/40) だけでなく claims を精読 (利用者指摘):
- 再走の過剰 open はジャンクでも再開設でもなく**開設に値する新規事象** (StopAndProtect /
  ジェックス JP ランサム / FUXA SCADA 等)。production の選択も同様に妥当。
- 3 run の突き合わせ: base 再走は production 自身の開設 5 件中 **0 件を再現**
  (s16 は 2 件回収)。同一モデルが自分の選択を再現できない —
  **多数の妥当候補 × 開設枠 5 の選抜くじ引き**が正体 (再構築ドリフト + 温度)。
- 帰結: ①ML 化 (score+閾値) は品質改善でなく**原理的必然** (安定・監査可能・再現可能な
  選抜は score でしか得られない)。②ラベルは **記事単位の結果**で付与 (くじ引きの遅延
  開設を正例化)。③s16 スワップ問題は消滅 — 確率的挙動同士の比較に意味なし。detect は
  base 凍結、ML で置換。④unassigned の翌 run 再浮上により、漏れの多くは恒久でなく遅延
  — ML+毎時化はこの遅延の圧縮として効く。⑤self-agreement プローブは不要 (内容が回答)。

## 36. detect ML = 棄却 (2026-09-10 午後) — 代替は「LLM 独立採点 + code 閾値」

結果ラベル v2 (5,253 件、正 384 = 開設成功 164 + 真の見逃し/遅延 220。「既存事象への
吸収 458 件」は開かなくて正しかった = 負例へ) で時系列分割評価:

| 同量運転 (22 open) | 回収 |
|---|---|
| 現行 LLM (base 26B) | **19/40 (47.5%)** |
| メタ特徴 RF | 1/40 |
| 埋込 1024d + メタ LogReg | 3/40 (3 倍量でも 7/40) |

**ML 仮説は棄却** — 「新規追跡を開く価値」は浅い特徴に写らず (08-31「埋込は書式」が
ここでも支配)、ペア ML の成功 (関係構造の特徴) は移植不能だった。§34 決定木の型 5 の
処方 (score+閾値) は正しいが、**score の作り手は ML でなく LLM**:

- 代替設計: **LLM が記事ごとに独立採点 (0-5) → code が閾値決定** — 選抜の相互依存
  (くじ引き) が消え、安定・再現・Recall ダイヤルの §33 価値は全部残る。毎時 150 件
  × ~2s ≈ 5 分で毎時化も成立。deep-dive selector と同型。採点は後日蒸留可。
- 資産: ラベル 5,253 件 = 以後の detect 実装の凍結審判 (合否線 = LLM 基準 42.7% recall
  超え + 遅延開設 220 件の回収率)。
- 教訓: 型 3 (結果ラベル ML) の適用条件に「**決定関連構造を特徴量に写せること**」を
  明記 — 写せない意味判定は型 2/5 の LLM 側に残る。

### §36 追記: v3 = LLM 抽出特徴量 + ML 結合層 (2026-09-10 夕、利用者提案)

「LLM に処理させた特徴量を追加するのは？」 — ペア ML の勝ちパターン (llm_same を
特徴量に) の detect への正しい適用で、「生スコア + 閾値」案の上位互換 (結合層が
LLM 信号を**結果ラベルで較正**する — LLM 自身の recall 47.5% を現実の成長で再重み付け)。

- 抽出器: s16・記事ごと独立 (くじ引き構造なし)・schema 固定 {open_score 0-5 /

- 結合層: RF (JSON 木 export で本番は依存なし適用 — pair_model と同形式) に

- 審判: 既存の時系列分割 (test 968 / 正 40)。合否線 = 同量 19/40 超え。

## 45. detect の再評価 — 採点表が現行由来だった / 目標は「取りこぼさない」(2026-09-15)

### §45 追記: 判定の本体は「重要度」ではなく「追跡価値」(利用者指摘)

> 無制限に台帳が開設されるわけにはいかないので、この部分で**追跡すべきか否かの判定**が
> 重要になってくる

枠が有限である以上、問題は「どれだけ開けるか」でなく「**開く価値のあるものを見分けられるか**」。
そして現行の 2 方式とも、この判定を明示的に行っていない:

| 方式 | 明示している基準 | 追跡価値の扱い |
|---|---|---|
| 現行 detect (`detect_new.j2`) | PIR 直結 > 日本関連 > 政策 > 地政学 = **重要度の序列** | 規則に「単発の戦況報道・既知紛争の日々の推移は開かない」と**暗黙に**混在 |
| 独立採点 (`detect_llm_features.py`) | open_score = 「新しい」×「大きい」、mission_fit、severity = **すべて重要度** | **軸が無い** |

これで §45 の中身の差が説明できる: 独立採点が選んだ CVSS 10 の Entra ID RCE / Citrix
Pre-Auth RCE は **勧告 1 本で完結しうる**。現行が開設した 酒類販売 F 社 の漏洩 / PC メーカー G 社 の
ドライバ混入は小さいが **続報が積み上がる** (被害範囲・原因・帰属が後から判明する)。
**現行は追跡価値を暗黙に見ており、独立採点は重要度だけを見ている** — 採点表の勝敗ではなく
ここが本当の差だった可能性が高い。

→ 審判 (`build_detect_goldset.py`) は **importance (0-3) と trackable (0-3) を別々に**
聞く形にした。同じ軸で聞くとこの区別が測れないまま凍結されてしまう。
trackable=0 の定義は「**1 本で完結する** (勧告・パッチ公開・分析記事・制裁発表・統計)。
重要でも 0 になりうる」。

この分離が効けば、detect の改善は「モデルを替える」でも「枠を広げる」でもなく、
**判定軸を足す**ことになる (プロンプト = 可動部)。追加学習もこの軸を教えるものになる。

### §45 追記 2: 勧告は「見送り」でなく「見張り」— watch 軸の追加 (2026-09-15 利用者指摘)

> CVSS 10 の Entra ID RCE もそれを悪用した事象まで追えるのであれば価値はある。
> この場合は、関心に関連する**悪用した事象の方から**解説されるのが筋

追跡単位は脆弱性ではなく**それを悪用した事象**。勧告の段階では「誰が・どこを・いつ」が無く、
ACH にかける対立仮説が立たない (判定の材料が存在しない)。悪用が観測されて初めて被害範囲・
帰属・手口という続報が積み上がる。

**受け皿の現状**: 悪用の検出は既にある (`src/tools/kev_client.py` = CISA KEV との決定論照合、
routing の `has_kev_or_active_exploit`)。欠けているのは**勧告を見張る置き場**:

| 段階 | 受け皿 |
|---|---|
| 勧告 (CVSS 10 公開) | **無い** — situation を開かなければ `rejected` の 1 行だけ |
| 悪用の観測 | KEV 照合 ✅ |
| 悪用事象の追跡 | situation ✅ |

指標 (`situation_forecasts`) は situation にぶら下がるため、開かなかった勧告には
「CVE-X の悪用が観測されるか」を掛ける場所が無い。**見送った瞬間に視界から消える** —
detect が CVSS 10 を開きたがるのは、この構造的圧力が原因かもしれない。

→ 審判に **watch (bool)** を追加。「いまは追跡単位にならないが、悪用・被害が観測されれば
なる素地があるか」。**open=false でも watch=true はありうる** (見送りと見張りは別)。
これが無いと両者が同じラベルに潰れ、watch 層を作るべきかの判断材料が永久に失われる。

### §45 追記 3: 審判に聞かないこと / 集計の単位

点検して**審判に聞くべきでない**と判断したもの (どちらもデータから導出できる):

- **初報か続報か** — `situation_evidence` の割当履歴で分かる。審判に聞くと、記事単体では
  判断できないものを推測させることになる
- **既存事象へ吸収すべきか** — 同上。審判に聞くなら能動情勢 135 件のタイトルを毎回
  prompt に載せる必要があり (~3.6k tok × 190 件)、CoT 収穫より高くつく

⚠ **集計は事象単位で行う** (記事単位ではない)。同一事象の記事が 3 本あれば 1 本開けば正解で、
残り 2 本を「見逃し」と数えてはいけない (2026-08-31「ペア単位 88% を製品の成績として
語らない — 群単位 83%」と同型)。群化には既存の pair 判定を使う。

## 52. 単一事象の追跡と、積み重ねの追跡は別物 (2026-09-19、利用者の整理)

detect の審判で地政学を測ろうとして枠組みの誤りに気づいた。経緯: 利用者「地政学関連でも追う価値の
あるものは追った方がいい」→ 審判の任務定義に地政学を追記 → 「地政学で追跡価値のある事象が
引っかかるか検証したか」→ **陽性対照を作って否**が判明 → 利用者「単一事象の追跡と、単一事象を
積み重ねた追跡は別物ということですね」。

### 陽性対照 (台帳の実績で測る)

revision 3 件以上ある地政学系 (political / military / geopolitical / economic / information) の
event 情勢に、証拠として使われた記事 1,591 件。うち審判済み 34 件:

| 審判 | 件数 | 追跡価値の分布 |
|---|---|---|
| 開設 | 1 | 0: 26 / 1: 7 / 3: 1 |
| 見送り | 33 | |

ML の確率は中央 0.01、0.5 以上が 60/1591。**70 件の revision が積み上がった情勢の記事を、
審判もモデルも「1 本で完結する」と判定している**。

### 原因 = 追跡の単位が 2 種類ある

| | 単一事象の追跡 | 積み重ねの追跡 |
|---|---|---|
| 境界 | 出来事そのもの | 問い・主題 |
| 続報の意味 | **その出来事の姿が埋まる** (被害範囲・原因・帰属) | **別の出来事が足されて趨勢が動く** |
| 終わり | 判明しきれば閉じる | 閉じない |
| 例 | 侵害インシデント / 実悪用の脆弱性 | 米中の技術覇権 / 対日レアアース規制 / ウクライナの攻撃範囲 |

審判の `trackable` は前者しか測れない (「この記事が述べている事象そのもの」を問うため)。
地政学の個々の記事は完結していても、**束ねると動き続ける**。
→ **審判基準は detect (単一事象の新規開設) としては正しい**。地政学を任務定義に足したのは
誤った場所への対処だった (6 番目「日本利用者のいる共通基盤への侵害」だけが正しい修正で、
5 件が見送り→開設に変わった)。

### 実害 = 積み重ね型が event として開設され、更新枠を食っている

- **revision 20 件以上の情勢 26 件が、全 revision 2,259 件のうち 1,021 件 (45%) を消費**
  (standing 9 問の合計は 238 件)。
- うち地政学・軍事・経済の 8 件 (米イラン相互攻撃 70 / 対日レアアース 62 / ウクライナの攻撃範囲 54 /
  米中インフラ排除 46 / 北朝鮮製ミサイル 45 / MATCH 法 29 / 中国のアフリカ港湾 28 /
  イラン金融制裁 20) は **7 月の開設から閉じる見込みがなく証拠が入り続けている**。これは event で
  なく**問い**。
- 直近 3 日の再評価は event/cyber_incident 141 に対し event/geopolitical 19・military 11 —
  09-18 に問題にした「更新の繰越 20-75 件」の一因がここ。

### 整理 (段階)

1. 積み重ね型の 8 件を **standing (常設情報要求) へ移す**。問いの形に書き直し、証拠収穫は
   standing の宣言的な証拠条件 (型 E 趨勢 / H 閾値) に載せる。
2. event の更新枠が空き、単一事象の繰越が減る (期待: 毎時 6 件 + 朝夕 12 件で追いつく)。
3. detect の審判・ML は単一事象に限って評価する (地政学を detect の指標から外す)。
4. 積み重ねの成績は別指標で測る: standing の問いごとに「証拠供給率」と「答えが動いた回数」。

### §52 追記: 移行ではなく予算の配分にした (2026-09-19 午後、利用者判断)

## 54. 干渉の正体を測った — expert 選択は不適、直交部分空間が残る (2026-09-19)

§53 の 3 課題目の干渉に対し、利用者「他に可能性はないか、論文調査などして確認して」。
調査で 5 系統が挙がり (MoE-Sieve の expert 選択 / O-LoRA・OPLoRA の直交部分空間 /
TIES・DARE のアダプタ統合 / mSFT のデータ混合管理 / DoRA・PiSSA 等のパラメータ化)、
**このモデル固有で最も有望だった expert 選択を実測で棄却した**。

### 実測 (`data/mlx/measure_expert_usage.py`、Router を包んで top_k_indices を数える)

Gemma 4 26B = 128 experts / top-8 / 30 層。3 課題 × 4 例 × 3,000 tok の forward:

| 課題 | 使われた expert | 上位 32 (25%) の占有 |
|---|---|---|
| 事象ニュース | 128/128 | 37% |
| spotlight | 128/128 | 36% |
| 状況総括 | 128/128 | 37% |

| 課題間の重なり (上位 32) | |
|---|---|
| 事象 ∩ spotlight | 26/32 (81%) |
| 事象 ∩ 状況総括 | 24/32 (75%) |
| spotlight ∩ 状況総括 | **28/32 (88%)** |

- ⭐ **routing が集中していない**。MoE-Sieve (2026) の前提「上位 25% が大半を担う」が成り立たず、
  25% が 37% しか占めない (均等分散なら 25%)。狙い撃ちの余地が無い。
- ⭐⭐ **課題間の重なりが 75-88%**。干渉の正体は「同じ expert を奪い合っている」で正しかったが、
  **expert 単位では分離できない**。特に spotlight と状況総括が 88% — どちらも長文生成で当然。
- ⭐ **層数を上げる案も消えている** (Gemma 4 26B は 30 層 = 既に全層、§53 訂正)。
  容量の軸 (層・expert) は使い切っており、残るのは**更新の方向**を制御する手段。

### 残る選択肢

| 手段 | 適合性 | 実装コスト |
|---|---|---|
| expert 選択 (MoE-Sieve) | **棄却** — routing が分散し課題間で重なる | — |
| **O-LoRA / OPLoRA (直交部分空間)** | **適合** — 重なりが大きいほど意味が増す (同じ空間を共有したまま更新方向を直交させる) | mlx_lm に無い。射影を自前実装 |
| **TIES / DARE (アダプタ統合)** | 適合 — 学習を分けたまま 1 本にする | 課題別に 3 本学習 + 統合の実装 |
| mSFT (データ混合管理) | 補助 — 干渉自体は消えない | checkpoint 評価の自動化 |
| 課題別モデル (現状) | 確実 | 済 (GPU 常駐 3 本) |

⭐ **「容量を増やす」から「更新の方向を制御する」へ問題が移った**。層も expert も使い切った以上、
足し算では解けない。

### §54 訂正: 手持ちの 2 本は「別課題のアダプタ」ではない — 統合案の前提が崩れた (2026-09-19)

TIES / DARE を手持ちの n17m30 と n17c で試そうとして、データセットを突き合わせた:

| | 学習行 (重複除去) | 内訳 |
|---|---|---|
| n17m30 (`dataset_n16`) | 835 | 事象ニュース + 週次深掘り + spotlight |
| n17c (`dataset_n17c`) | 953 | **上の 835 行を完全に含む** + 状況総括 CoT 118 行 |

`config_n17c.yaml` の先頭にもそう書いてある (「n17m30 混合 1,141 + 状況総括 CoT x3」)。

⭐⭐ **TIES / DARE / task arithmetic は「別々に学習した課題ベクトル」を前提にする**。
手持ちの 2 本は入れ子の同一系列で、n17c は n17m30 の上位互換の学習をした 1 本の再学習にすぎない。
両者を足しても課題ベクトルの合成にはならず、**同系列の 2 checkpoint の内挿 (model soup / WiSE-FT)**
にしかならない。§54 の表で「アダプタ統合 = 有望、学習不要」と書いたのは、この確認をせずに
研究の枠組みだけを当てはめた誤り。

⚠ **論文の手法を採る前に、手持ちの資産がその手法の前提を満たすか確かめる**。
今回は「学習不要で試せる」という魅力が先に立ち、前提 (課題ベクトルが別々であること) の確認を
後回しにした。⭐ **干渉は「別々に学習した 2 本を足したとき」ではなく「1 回の学習で 118 行を
足したとき」に起きている** — これは統合の問題ではなく**混合学習の問題**である。

### 実験の形を正す

| 手 | 前提 | コスト |
|---|---|---|
| **内挿 (soup)** n17m30 ↔ n17c | 前提なし (同系列 2 点) | 学習不要。fuse 1 回 |
| **課題ベクトル統合** | **CoT だけで学習した 1 本が要る** (未作成) | 学習 1 本 (354 例、短い) + fuse |

内挿が先。退行が「程度の問題」(書き続ける挙動が強すぎる) なら、古い側へ寄せるだけで
spotlight / 事象ニュースが戻り、状況総括の改善がどこまで残るかが測れる。戻らなければ
「程度ではなく質の変化」と分かり、課題ベクトル統合 (CoT 専用アダプタの学習) へ進む根拠になる。

数式の道具立ては用意した (`data/mlx/merge_adapters.py`)。mlx_lm の LoRA は
ΔW = scale·(B@A) で **scale は rank に依らない定数**のため、rank 方向に連結すれば
w1·Δ1 + w2·Δ2 が**近似なしで**出る (実テンソルで検算、誤差 1.5e-7 = float32 の丸め)。
内挿にも課題ベクトル統合にも同じ script が使える。

### §54 追記: 退行は損失に映らない — 重みの選定は生成でしかできない (2026-09-19 16:10)

内挿の重みを fuse せずに選ぶため、**学習と同じ損失** (`mlx_lm.tuner.trainer.evaluate`、
mask_prompt=True) で 3 課題の検証例を測った:

|---|---|---|---|---|
| n17m30 | 1.0680 | 0.6344 | 0.9414 | 0.8813 |
| n17c | 1.1136 | 0.6838 | **0.6887** | 0.8287 |

⭐⭐ **CoT 学習の退行は損失に出ていない**。凍結審判では事象ニュースが 2 勝 12 敗、
冗長が 1.34 → 5.66、spotlight は key_events 126 件 (仕様 5-8) の暴走だったのに、
損失の差は **+0.05 nats (5%)** しかない。

理由は明快で、**teacher forcing では常に正しい前文が与えられる**こと。「自分で書いた
続きを見て、まだ書き続ける」という挙動は、正解を毎 token 差し込む評価では原理的に
現れない。⭐ **生成の暴走は生成でしか測れない**。

- 学習中の val 損失で checkpoint を選ぶのは、**この種の退行に対しては盲目**。
  §37 の epoch 曲線で「val 最小が最良ではなかった」と書いたのと同じ穴の、より鮮明な例。
- 逆に言えば、損失は **表現としては保たれている**ことを示す。n17c は 3 課題とも
  ほぼ同じだけ「知っている」。壊れたのは停止の判断であって知識ではない。

よって重み選定は生成で行う (`data/mlx/screen_runaway.py`)。fuse を候補ごとに回さずに
済むよう、mlx_lm でアダプタを付けたまま凍結 prompt を生成し、**生成長と key_events 数**
で止まるかどうかだけを見る (Ollama の grammar は使えないので JSON は崩れうるが、
測るのは「止まるか」なのでそれで足りる)。
