# n 系 (長文生成) の計画 v3 — クラウド学習の教訓を反映 (2026-09-28)

対象: 事象ニュース (event_news)・Spotlight・状況総括 (synthesis narrative)。本番は
n17m30 (事象ニュース・深掘り) と n17c (状況総括・Spotlight・detect) の 2 本常駐。

## 0. 前提 — ここまでで分かっていること

| 事実 | 出典 |
|---|---|
| 1 本の LoRA に長文 2 課題を混ぜると干渉する (n17m、n18 とも不合格) | SYNTHESIS §53-54 / n18 の公平再評価 |
| n18 (3 課題統合) は要点が痩せ、元記事より強い断定 9.2% (n17m30 0%)。事象の対読 n17m30 27 : n18 4 | 要点照合 v3 |
| 状況総括の暴走は文法の文字列上限が原因 (上限は生成後に決定論で切る) | 09-26 |
| 評価と本番の形 (CoT・schema・think) のずれで判断を誤った | 09-26 |
| **本番の n 系はすべて think=False。MLX の学習は思考の印つきの形 = s 系と同じずれ** | 09-28 実測 |
| **本番の think=False は空の思考欄を付けない。付けて学習すると JSON 制約下で崩れる** | 09-28 (v2a/s20pf の暴走 60%) |
| **bf16 元モデルで学習した LoRA は Ollama int4 で効果が大きく落ちる (int8 は可)** | 09-28 (v2b-q4 暴走 10% / q8 2%) |
| 教師 (Opus) は定番の ATT&CK 技術を当て推量で付ける (教師の要約の技術の 54% が推測) | 09-28 Opus 判定 |
| Opus を教師・審判にすると、悪用の詳細を含む窓が安全機能で系統的に抜ける | 要点照合 v3 (Redis PoC) |
| Opus の審判は利用上限 (429) で止まる (09-26 に 2 系統が途中停止) | n18 公平再評価 |

## 1. 方針

- **学習はクラウド (RunPod H100) に移す**。MLX は 17 時間・その間本番停止。クラウドは 3-4 時間・$11-15・本番は止めない
- **1 課題 1 モデルを既定**とし、統合は「統合しても要点照合で劣らない」ことを測れたときだけ行う
- **教師データは量より質**。s 系で効いた掃除 (契約外の欄・ナビ残骸・当て推量) を n 系にも適用する
- 採用の判定は **要点照合 v3 (被覆・断定) + 盲検の対読 (中身を読む)**。件数の勝敗だけで決めない

## 2. 段取り

### N0 — GPU 不要 (今すぐ)
1. **本番の形の実測**: 事象ニュース・Spotlight・状況総括の本番呼び出しを 1 回ずつ再現し、
   `prompt_eval_count` と学習スクリプトの入力長が一致することを確かめる (system の有無・CoT 欄・schema)
2. **教師データの監査** (1,495 例):
   - 契約外の欄・ナビ残骸の入力 (s 系と同じ決定論の検査)
   - 出典番号・引用の実在 (既存の引用実在チェックを教師にかける)
   - 断定の強さ・但し書きの脱落: Opus で 100 例を抜き取り判定 → 率を見て全件判定するか決める
   - ATT&CK・アクター帰属の当て推量 (s 系の判定スクリプトを流用)
   - Opus が安全機能で拒否・欠落させた窓の洗い出し (教師の空白を知る)
3. 審判の実行計画: Opus の枠の残りを見て、同時数と Sonnet への振り分けを決める

### N1 — 較正: クラウドで n17m30 を再現 (1 本、$11-15)
- n17m30 と同じデータ・設定 (事象ニュース + 圧縮 Spotlight、30 層 rank 32)。変えるのは
  **学習の形 (本番と同じ入力) と経路 (PEFT) だけ**
- int8 で取込み、事象ニュース凍結 38 窓で n17m30 と比較: 要点照合 v3・暴走・契約外の欄・対読
- 目的: クラウド経路が長文でも MLX と同等以上になることの確認 (s 系の較正 s20pf に当たる)

### N2 — 量子化の決着 (s 系で先に、$11)
- v2c を「4bit に量子化して戻した重み」を元モデルにして学習 (MLX と同じ QLoRA 型) → int4 で配備できるか
- v2c (bf16 元・int8) と比較。**同等なら n 系も QLoRA 型にしてメモリを int4 のまま保つ**
  (常駐 3 本を int8 にすると 27GB × 3 = 81GB、別プロジェクトの 20GB と合わせて窮屈)

### N3 — 課題別の本学習 (N1・N2 の結果を反映)
- 事象ニュース: N1 に N0 の掃除を入れた版
- 状況総括 + Spotlight: n17c 相当をクラウドで (同様に掃除・形の修正)
- 各々を現行と比較し、合格したものから差し替え (s 系の採用チェックリストと同じ手順)

### N4 — 欄の順番 (推論を先に) の双子比較
- 事象ニュースは「結論が先」の逆順で、n18 の断定は bluf で起きた。教師の欄順を入れ替えた版と
  入れ替えない版を **同じレシピで並行学習** (クラウドなら 2 本同時に 3-4 時間) し、断定率を比べる
- 段階 1 (学習なしで並べ替え) は学習外の並びで崩れたため、判断材料にしない

### N5 — 深掘り (未学習の課題)
- 深掘りには教師データが無い (SYNTHESIS §62)。教師の収穫を設計してから (外部枠を使う)

## 3. 判定の物差し (すべて本番と同じ形で生成してから測る)

| 観点 | 物差し |
|---|---|
| 要点の網羅 | 要点照合 v3 (Opus のシート + Sonnet の照合)、全要点 / 核心 |
| 断定の強さ | 要点照合の「確度の格上げ」率 (現行 0%、n18 9.2%) |
| 崩れ | 暴走 (反復・長さ)・JSON の途中切れ |
| 形式 | 契約外の欄・出典番号の実在 |
| 中身 | 盲検の対読 (Opus)。**数字と中身が食い違ったら中身を読んで決める** |
