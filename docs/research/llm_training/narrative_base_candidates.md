# narrative 族の基盤候補 — 26B 以外の考察 (2026-09-05)

「軽量モデルで全 narrative」の車両として gemma4-26B-a4b 以外を検討する。
前提: パイプライン自動化により**基盤 1 つの実測検証 ≈ SFT 2-4h + 評価 1.5h** まで
下がっており、紙上の比較でなく A/B できる。教師対 2,273 と凍結評価 3 セットは
モデル非依存で持ち運べる。

## 要求仕様 (narrative 族)

- 日本語の**生成品質** (留保・但し書きを自然に書けること)
- 速度: 事象ニュース ~85 件/日 + spotlight 21 PIR/日 + 将来の総括。
  **1 件 30-40 秒以内なら成立** (毎時バッチ数件のため。triage の 2,000/日とは別の要求)
- 中国系不可 / ローカル完結 / SFT の反復コスト

## 考察

1. **GPT-OSS-Swallow 20B が「26B の正面のライバル」**。同じ MoE-高速級 (A3.6B) で
   JP 特化済み・Apache 2.0。**gpt-oss アーキは手元の Ollama で稼働実績があり** (gpt-oss:20b
   を pull 済み)、gemma4 で苦労した本体変換の一部が既に舗装されている可能性がある。
   検証すべきは (a) harmony 形式下での `generate_structured` の挙動 (b) mlx-lm での
   LoRA 学習可否 (c) fuse→GGUF 経路。
2. **CALM3-22B は「dense の反復速度を取りに行く」選択**。narrative の品質要件を dense
   22B が満たし、かつ 1 件 30-40 秒に収まるなら、MoE の変換 1 時間/回が消えるのは
   反復開発上大きい。まず素の 22B の速度と JP 生成を 1 時間で実測できる。
3. **Swallow 8B は narrative には賭けになる** (文献: 自由 narrative は容量が効く)。
   ただし**構造化族 (triage/抽出) の車両としては第一候補**のまま。
4. 31B dense は品質最高だが速度で失格 — ただし**教師・審判役** (goldset 生成の
   ローカル代替、夜間バッチ) としての価値は残る。

## 推奨する検証順序 (今夜の結果後)

```
1. v1 vs 31B (今夜自動) → 26B 特化がそもそも 31B を超えるかの基準点
2. GPT-OSS-Swallow 20B の疎通 PoC (半日):
   pull → schema 付き 5 件生成 → JP 品質目視 → mlx-lm LoRA 1 epoch 試走
3. 成立すれば同一データ・同一評価で 26B 特化と A/B (SFT 2-4h + 評価 1.5h)
4. CALM3-22B は素の速度実測 (1h) で足切り判定してから同様に
```

⚠ どの候補も「26B より良い」ことを**同じ物差し (3 凍結セット + 床)** で示してから
乗り換える。今日の教訓: 移行判断を紙上の性能表でしない。
