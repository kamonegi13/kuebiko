# s 系 (判定・抽出) 多課題 LoRA の学習要領 v2 — 設計 (2026-09-27)

s20 の評価で見えた問題 (知識の低下・要約の暴走・契約外の欄・言語の混入・重要度の偏り) を、
**学習データの監査・手元の実測・文献** から原因に分け、次の学習要領を設計する。
既存ノート (SYNTHESIS §0-65・catastrophic_forgetting・lora_composition・evaluation_methodology・
multitask_interference・distillation_transfer) の結論を前提にし、ここでは差分だけを書く。

## 0. 不変条件 (過去の実測で繰り返し確認済み — v2 でも破らない)

1. 層数は 8 に戻さない (§42-43: 層数が最大の梃子)
2. 出力スキーマの違う長文生成課題は 1 本の LoRA に混ぜない (§19・§42 追記)
3. 組み立て側のトークン上限 < 学習側の max-seq (09-22 の NaN)
4. 採否は **差分の中身を読んで** 決める。件数・val loss・平均・一致率だけで決めない
   (09-21 / 09-27: 集計だけで推奨して 2 度誤った)
5. mlx-lm の標準学習ループを使う (自作ループは既知の不具合 2 件で高リスク — catastrophic_forgetting)
   → **損失関数を変える手法 (DITTO・unlikelihood・トークン重み) は後回し**。データ側の手を先に打つ

## 1. 診断 — s20 の問題はどこから来たか

### 1.1 学習の設定 (s17 と s20 は「データの違い」と「規模の違い」が交絡している)

| | s17 (本番) | s20 |
|---|---|---|
| 層 / rank / lr | 8 / 8 / 1e-5 | 30 / 32 / 3e-5 (mlx の scale 10 は直接の乗数 → 実効はさらに大) |
| 対象 | — | **router にも LoRA** (rank 32。診断ノートは「router を外す」を推奨していた) |
| 例数 / 反復 | 5,644 / 1,400 | 5,024 / 5,024 (1 周) |

忘却は学習するパラメタ数と更新回数のべき乗則で増える (Kalajdzievski arXiv:2401.05605)。
**s20 の知識低下と暴走の増加は、データでなく規模で説明できる可能性がある** — 未切り分け。

### 1.2 損失の配分 (手元のコードで確認: mlx-lm 0.31.3 `default_loss`)

batch 1 で 1 例の中のトークン平均を取り、勾配蓄積でも均等に平均する → **どの例も長さに関係なく同じ重み**。
課題の重みは例数だけで決まる。

| 課題 | 例数 | 勾配の配分 | 出力 (中央) | 備考 |
|---|---|---|---|---|
| pair | 1,494 | **29.7%** | 141 tok | 9/8 実測で **SFT により回答が 1 問も変わらない** (§26) |
| pir | 787 | 15.7% | 29 tok | |
| summary | 785 | 15.6% | 863 tok | 1 トークンあたりの重みは種別の約 1/100 |
| triage | 737 | 14.7% | 29 tok | |
| kind | 591 | 11.8% | 9 tok | |
| ach | 375 | 7.5% | 972 tok | 同じ入力に 2〜7 通りの教師 (言い換え。判断は一致) |
| detect | 255 | 5.1% | 2,262 tok | **完全一致の複製 170 件** (×3) = 重み 3 倍と同じ |

→ **勾配の 3 割を、出力が変わらない課題 (pair) に使っている**。長い JSON の後半 (閉じの判断) の
1 トークンあたりの重みは小さい (暴走との関係は仮説)。

| 検査 | 結果 | 判定 |

| 教師出力の JSON・繰り返し・「de」の混入 | 0 件 | ✅ **s20 の「de」は教師由来ではない** |

| **要約の契約外の欄** | bluf 785/785・pmesii 768・diamond 618・event_date 552 | ❌ 本番では出させない欄。s20 が出す原因 (接頭辞の有無と無関係と実測) |
| **入力がナビの残骸の要約** | 40 件 | ❌ 教師が「本文なし」と書いたうえで **見出しや自身の知識から推測を書いている** (例: GIMP の版の沿革) → 作り出しを教えている |

### 1.4 今日の実測 (s20 の暴走の切り分け、同じ 300 件)

| 腕 | 暴走 | 「de」 | bluf を出す |
|---|---|---|---|
| s20 接頭辞あり | 4 (1.3%) | 10 | 165 |
| s20 接頭辞なし | 1 (0.3%) | 14 | 159 |
| s20 アダプタ 7 割 | (集計中) | | |
| s17 (先頭 150) | (集計中) | | |

接頭辞は契約外の欄にも「de」にも関係しない。暴走の 4 対 1 は有意でない (p≈0.37)。

### 1.5 CTIBench の低下 (500 問 MCQ)

base 355 / s17 348 / **s20 317**。採点は生成した文字から A-D を正規表現で抜く方式で、
**書式の崩れと知識の喪失を区別できない**。Spurious Forgetting (ICLR 2025, arXiv:2501.13453) は、
低下の多くが「知識の喪失でなく課題への整合の崩れ」だと示す。→ 対策の前に切り分けが要る (§3 E0)。

## 2. v2 の学習要領

### 2.1 学習前の関門 (データ) — 新設 `scripts/audit_sft_dataset.py` を assemble の最後に必ず通す

| 関門 | 処置 |
|---|---|
| 契約 | 教師出力を **本番のスキーマで検証**し、契約外の欄 (要約: bluf・pmesii_axes・diamond・event_date・event_date_basis・compromise_date・article_type・editorial_stance・routing_flags) を **消してから** 書き出す |
| 入力の質 | 本文がナビの残骸・文字化け・空の例は **除外** (教師に「推測で埋める」例を学ばせない)。本番側も同じ判定で要約を止めるのが筋 (別件) |
| プロンプトの同一性 | 学習のプロンプトを本番の組み立て関数で作り直した文字列と突き合わせる (「(teacher)」のような食い違いを検出) |
| 系列長 | 実トークン数 < max-seq (既存) |
| 出力の質 | 反復・言語混入・壊れた JSON は除外 (現状 0 件だが関門として残す) |
| 複製 | 完全一致の複製は **意図した重み付けとして明示** した場合のみ (§2.2 の表で管理) |
| 汚染 | CTIBench の設問・CVE ID・ATT&CK ID・アクター名をブロックリストにし、知識データ (§2.3) と照合 |
| 生成元 | 例ごとに教師モデル名を記録し、禁止リスト (FORBIDDEN_MODEL_PREFIXES と同じ思想) で検証 |

### 2.3 CTI 知識データ (忘却の抑制)

- **出典**: MITRE ATT&CK (STIX)・CAPEC・D3FEND・CISA KEV・Sigma・Atomic Red Team (いずれも学習利用可のライセンス)。
  ATT&CK / CWE / NVD は CTIBench の出題元なので **ID と 8-gram で除染**
- **使わない**: Primus-Reasoning (CTIBench から生成 + DeepSeek-R1 = 汚染と中華系の二重)・DeepSeek/Qwen 蒸留系・SecBench (中国発)
- **形**: 用語・技術の説明 QA、「この手口はどの技術か」の短い分類、防御策の対応 (D3FEND)。日本語で書く
- **正解の書き手**: 公式の説明文を **本番の base (素の Gemma) に渡して言い換えさせる**
  (SDFT arXiv:2402.13669 の「base 自身の言葉で書くと KL が小さく忘れにくい」と、公式文による接地の両立)。
  base が誤る箇所は公式文と照合して落とす
- ⚠ 「CTI 知識 QA を混ぜると CTI 知識ベンチが保たれる」を直接示した論文は無い (Primus は一般会話 339 例 + 事後の統合、
  Foundation-Sec は「事後学習で知識を教えない」方針)。**効果は E3 で測る**

### 2.4 LoRA の設定

| 項目 | s20 | v2 案 | 根拠 |
|---|---|---|---|
| 層 | 30 | 30 (下位 2 層を凍結は E2 で試す) | 不変条件 1 / Spurious Forgetting (下位層の凍結が有効) |
| rank | 32 | 32 | 変種 (DoRA・PiSSA・rsLoRA) は lr を調整した素の LoRA と同等以下 (arXiv:2601.22708) |
| router | LoRA あり | **外す** | 既存の診断ノートの推奨が未反映。router は影響の大きい部位 (arXiv:2608.07890、間接証拠) |
| lr | 3e-5 | **2e-5** | lr が小さいほど汎用能力が残る (arXiv:2509.20758) / 忘却は更新量のべき乗 (2401.05605) |
| scale | 10 | 10 で学習し、**統合時に 6〜10 を走査** | WiSE-FT (arXiv:2109.01903): base との内挿で頑健性が上がる。統合と取込は 1 本 49 秒 |
| 接頭辞 | あり | あり | 外すと種別が 277→257 (p<0.001) に落ちる (s19 評価)。契約外の欄とは無関係と実測 |

### 2.5 学習でなく配信側で直すもの

| 問題 | 処置 |
|---|---|
| 暴走 | 実装済み: 一覧の件数上限 (schema) + 3 型の検出で 1 回作り直し (ff5ea29a)。本番 45 日で誤検出 0 |
| 契約外の欄が本番に入る (PMESII の和集合) | 要約の PMESII を捨てる (プロンプトの規定どおり)。データ側の削除と両方で |
| triage の重要度の偏り | 学習で直さない (教師に揃った結果)。混同行列を見て閾値・後段の規則で較正 |
| 「de」の混入 | 教師由来でない。温度はクライアントが 0.3 を送っている。検出して作り直す対象に加えるかは頻度 (3〜5%) と害を見て判断 |

## 3. 実験計画 — 1 回に 1 変数

| 段 | 内容 | 費用 | 決めること |
|---|---|---|---|
| **E0** (学習なし) | ① CTIBench を「抽出失敗率」と「選択肢の対数尤度での採点」で採点し直し、base / s17 / s20 を同じ 500 問で McNemar。② s20 の scale を 6 / 8 / 10 で統合し、CTIBench・暴走率 (300 件)・課題の評価を測る | 半日 | 低下が **書式か知識か**。scale を下げるだけで足りるか |
| **E1** | データだけ直す (§2.1 の関門・§2.2 の配分・知識データなし)。設定は s20 のまま | 学習 1 回 (約 12 時間。例数が 2 割減) | データの修正の効果 (契約外の欄・作り出し・課題の性能) |
| **E2** | E1 のデータ + router を外す + lr 2e-5 | 学習 1 回 | 規模の効果 (知識・暴走・課題の性能)。ここで s17 との交絡が解ける |
| **E3** | E2 + CTI 知識 200 件 | 学習 1 回 + 知識データの作成 (半日) | 知識データの効果 |
| E4 (条件付き) | 下位 2 層の凍結 / 2 seed の統合重みの平均 / DITTO (自作ループ) | 学習 1〜2 回 | E2-E3 で残った問題に応じて |

各段の結果が出るまで次の段に進まない。E1 と E2 は独立に回せる (夜に 1 本ずつ)。

### 採否の基準 (各段で同じ評価を回す)

| 評価 | 合格の条件 |
|---|---|
| 課題 (pair / 種別 / triage / ACH / detect replay) | s17 に対して劣化なし (McNemar)。**差分の中身を PIR / スキーマの定義で読む** |
| 要約 (goldset 86 + 盲検の対比較) | 誤り・抜けが s17 どうしの揺れを超えて悪化しない。名前の欄は定義に照らして読む |
| 暴走率 (同じ 300 件) | 1% 未満 (配信側の作り直しがあるので、それ自体は致命でない) |
| 契約外の欄 | 0 件 |
| CTIBench MCQ (対数尤度採点) | base から 2pt 以内 (500 問の対比較の 95% 幅は約 ±2.8pt — 3pt 未満の差は判定しない) |
| 生成の指標 | 2 seed で確認 (学習し直しの分散 0.85〜1.54 倍 — §27) |

## 4. やらないこと (根拠つき)

- LoRA 変種 (DoRA・PiSSA・rsLoRA): lr を調整した素の LoRA と同等以下 (2601.22708)
- 別 seed の LoRA の A・B を混ぜる soup: 0.5:0.5 で正答率が 39% に落ちる (CoTo arXiv:2506.05713)。
  統合後の ΔW の平均は未検証 (E4 の候補)
- CTIBench 由来のデータ (Primus-Reasoning 等) の利用: 評価の汚染
- 継続学習での増分: データ量が梃子にならない (§40 / 09-11)
- 学習率や epoch を増やして性能を追う: 忘却と暴走の増加方向

## 5. 実測との対応 (この設計で確かめる仮説)

| 仮説 | 確かめる段 |
|---|---|
| s20 の知識低下は書式の崩れが主 | E0 ① |
| scale を下げれば知識と暴走が戻り、課題の改善は残る | E0 ② |
| 契約外の欄の出力は教師データが原因 | E1 (0 件になるはず) |
| ナビ残骸の除外で「見出しから作り出す」が減る | E1 (goldset のナビ 3 記事で確認) |
| pair の削減で他課題が伸びる / pair は落ちない | E1 |
| 規模 (router・lr) が知識低下と暴走の原因 | E2 |
| CTI 知識の混入で CTIBench が保たれる | E3 |
