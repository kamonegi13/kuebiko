# PageIndex (推論ベース・ベクトル不要の RAG) の調査 (2026-09-30)

## 何か
- 長い文書を目次のような**木構造 (章 → 節 → 小節) に索引化**し、質問時に LLM がその木を上から読み進めて
  該当の節を選ぶ。ベクトル DB もチャンク分割も使わない
- 開発: VectifyAI (英国ロンドン、2023 年創業・約 20 名)。MIT ライセンス。GitHub で約 3.8 万スター
- LLM 呼び出しは LiteLLM 経由。既定は OpenAI の API だが、OpenAI 互換の口 (Ollama 等) に向けられる。
  索引づくりで JSON 形式の要約を多用する (ローカルモデルの安定性は要確認)

## 宣伝の数字の読み方
- 「FinanceBench 98.7%」は自社の商用製品 Mafin 2.5 の自社評価。PageIndex 単体の独立評価ではない
- 解説記事の留保: 長い文書ほど有利 / 多数の独立文書の検索はベクトルが向く / 見出しの弱い PDF・
  OCR の誤り・変換の崩れに弱い / 質問ごとに LLM が木を何段もたどるので時間と費用がかかる

## kuebiko での位置づけ
| 用途 | 判断 |
|---|---|
| ニュース記事の集まり (事象ニュース・台帳・detect) | 向かない (短い独立文書が大量 = ベクトル・グラフの領域) |
| 長い一次資料 (ベンダーの脅威レポート PDF・政府の戦略文書・ドクトリン) | 向く。分析チャットで報告書の節を問う・深掘りで元の報告書まで読む、が候補 |
| GraphRAG との関係 | 補完。PageIndex = 1 文書の中を構造でたどる / GraphRAG = 事象と事象の間を線でたどる |

## 導入するなら
1. **依存の安全性**: LiteLLM は 2026 年に保守者の資格情報を奪われ PyPI に悪性版が出た事案がある。
   ライブラリごと入れず、**考え方 (節の木 + LLM が木をたどる) を自前で小さく実装**する方が CLAUDE.md §4 に沿う
2. 外部送信: 既定のままだと文書を OpenAI に送る。本番はローカルに向ける
3. ローカルの推論力: 木をたどる推論はモデルの力に依存。s21 / n19 は課題特化なので要検証
