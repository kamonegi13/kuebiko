## 0. 要約 (BLUF)

変更の入口が主題ごとに分散している (実際に散っているのは 4 箇所)。**専用ページは閲覧のみ、定義の変更は
設定カテゴリ**に寄せる。実行・再生成と承認キューは閲覧面に残す (定義の変更ではない)。

## 1. 旧基準を廃止した理由

旧基準 (2026-08-02):「配置の判断基準 = **対象画面を持たないものだけが設定ページに残る**」
— マッチリストは配信ルールの語彙なので情報フローへ、ソースは購読ソース、ジョブは実行管理。

根拠は「**対象を見ながら直せる**」だった。しかし 2026-09-16 の調査で、

> ⚠ **その「見ながら」が実装されていなかった**。マッチリスト編集画面 (`MatchListsView`) は
> **配信ルールを表示しておらず**、やっているのは保存後に `routing-rules` のキャッシュを
> 無効化するだけだった。

理屈だけが残り、変更の入口が分散する結果になっていた。

さらに「見ながら直す」を分解すると、必要なのは次の 3 つだけで、**いずれも編集対象に
付随するデータ**であり閲覧ページ固有のものではない:

| 見たいもの | 実体 | 既存 API (実装済み) |
|---|---|---|
| **効果** | この条件だと何が該当するか | `pirApi.preview` / `routingRulesApi.preview` / `sourcesV2Api.previewHtmlListing` / `promptRubricApi.testRubric` / `promptBlocksApi.previewBlocks` |
| **参照関係** | この定義を誰が使っているか | 一部のみ (下記 §4 の要件) |
| **成績** | いま何件拾っているか | SIR の KPI (7d / 30d / last_match / top_feeds / top_actors) |

効果の確認は**既に編集フローの機能**として存在する。よって「見ながら直したい」は
移設を妨げる理由にならない。

## 2. 分類 — 何を移し、何を残すか

2026-09-16 に `useMutation` を持つ全 35 コンポーネントを棚卸しした結果。

### A. 移す (定義の変更)

| 現在地 | 変更対象 |
|---|---|
| `/app/pir`, `/app/pir/edit` | SIR の作成・編集・承認・削除・有効化 |
| `/app/subscriptions` | ソース登録・編集・削除・折り畳み・表示名・信頼度 |
| `/app/jpci/operators` | 指定事業者名簿 |
| `/app` (ダッシュボード) | widget 配置 |
| `/app/config` 配下 (既に設定) | プロンプト block/rubric、モデルティア、LLM 接続先、システム、raw YAML |

⭐ **`/app/flow` (情報フロー) は移設不要** — nav の **「設定」グループ内**に既にある
(利用者指摘 2026-09-16)。配信ルール・チャンネル・プロダクト配信・マッチリストはすべて
ここに内蔵されており、新基準に**既に適合している**。むしろ良い先例で、編集と一緒に
`routingRulesApi.preview` (効果) を持っている。足りないのは参照関係だけ (S2)。

⚠ 私 (Claude) は当初これを「専用ページ」と誤分類した。**nav のグループ構造を見ず**、
ルート一覧とページ実体だけで分類したため。画面の所属は `nav.ts` の `NAV_GROUPS` が
SSoT で、ルートの有無では判定できない。

### B. 残す (実行・再生成)

| 面 | 操作 | 残す理由 |
|---|---|---|
| 実行管理 | ジョブ即時実行・有効/無効・再スケジュール | 「見て、すぐ回す」が成立している |
| 現況 / SIR | Spotlight 再生成 | **古いと気付いた面でその場で直せる** — 2026-09-16 に 18 日前の spotlight を SIR 詳細で発見して再生成した実例 |
| アクター辞書 | MITRE 同期 | 同上 |

⚠ ジョブの**有効/無効**は定義の変更に見えるが、実行管理に残す。運用中に止める操作で、
止めたい判断は実行状況を見て起きる。

### C. 残す (運用判断の記録)

| 面 | 操作 |
|---|---|
| 現況 (点検) | 編集レビュー、分類提案の承認/却下 |
| アクター辞書 | 新興アクター提案の承認/却下 |
| 記事 / 事象ニュース | メモ、翻訳実行 |
| 取込・処理履歴 | 履歴削除・purge |

**承認キューは判断対象を見ながら行う作業**で、設定に移すと対象を見られなくなる。

### D. 現状維持 (資格情報)

Webhook URL / Anthropic キー / Claude Code トークン / Ollama URL / IMAP /
Cloudflare トンネル。既に `CREDENTIAL_WRITE_PATHS` で遠隔から常時遮断 (§12)。

## 4. 各編集画面に課す要件

移設しただけでは旧基準と同じ失敗 (理屈だけで実装が伴わない) を繰り返す。
**移す画面には次を必須にする**:

1. **効果 (preview)** — 保存前に「この定義だと何が該当するか」を出す。
   既存 API があるものは配線するだけ。無いものは移設と同時に作る
2. **参照関係** — 「この定義を誰が使っているか」。
   例: マッチリスト → 参照している配信ルールの一覧 (**今は無い。新規実装**)
3. **成績 (KPI)** — 直近の該当件数・最終該当日時。SIR には既にある

⚠ 3 点が揃わない画面は移設しない。揃えてから移す。

## 5. 閲覧面からの導線

閲覧ページには**編集へのリンク**を置く (例: SIR 詳細の「この SIR の定義を編集」→
設定の該当箇所)。読みから書きへの移行が明示されるのは利点で、誤って定義を触る経路が減る。

⚠ リンクは**該当箇所まで**飛ばす (設定トップに飛ばすと探し直しになる)。

## 6. 段階

各段は単独で出荷でき、途中で止めても壊れない。

| 段 | 内容 | 出荷判定 |
|---|---|---|
| **S1** | 設定カテゴリの器を作る (群立て + 空の枠 + 既存タブの再配置) | 既存機能が新しい群立てで動く。移設ゼロ |
| **S2** | **参照関係**の実装 (マッチリスト → 配信ルール、SIR → 配信ルール) | 編集画面で「誰が使っているか」が見える |
| **S3** | 低リスクから移設: 指定事業者名簿、widget 配置 | 移設後も編集でき、閲覧面にリンクがある |
| **S4** | SIR の定義を移設 (KPI は既にある、preview も既にある) | 3 要件が揃った状態で移る |
| **S5** | 購読ソースを移設 | 同上 |
| **S6** | 旧入口の撤去 + 導線の点検 | 変更の入口が設定に一本化。閲覧面に定義編集が残っていない |

⚠ **S2 を S3 より先に置く**のは意図的。参照関係が無いまま移すと、旧基準と同じ
「理屈だけ」の状態を設定側に再現することになる。

⚠ **S6 で旧入口を消すまでは二重の入口が残る**。その間はどちらも同じ API を叩くので
壊れないが、**片方だけ直す事故**の温床になる (本プロジェクトで再発している型)。
S6 を先送りしないこと。
